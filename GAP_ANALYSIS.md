Automatic delivery later" — honored. `specs/016-webhook-events/spec.md:191-192` (FR-010): "In v1 the system MUST NOT perform any automatic delivery, dispatch, retry-of-delivery, or signing." ### 2.2 Promised and genuinely missing / partial

1. **Stalled-batch recovery is implemented but never runs.** Spec §26 and success criterion 33 (§39) require detecting batches lost to a dead Scrapyd node. `recover_stalled_batches` exists and is unit-tested (`apps/workers/app/workers/tasks_jobs.py:452-533`, `tests/unit/test_jobs_stall_recovery.py`) — but `grep -rn 'SCRAPE_RECOVER_STALLED' apps/ libs/` finds only the definition, the queue route (`celery_app.py:120`), and the constant (`task_names.py:19`). No enqueue site exists. `specs/008.../spec.md:150` says activation "needs the Celery beat schedule, which is delivered in SPEC-13" — SPEC-13 never mentions it (`grep -in 'recover|stall|beat' specs/013-scheduler/spec.md` → no relevant hits), and the scheduler loop enqueues only light-recheck/stats-flush/partition/rollup/retention plus the refresh pass (`apps/scheduler/app/scheduler/scheduler_app.py:218-240`). There is no `beat_schedule`/`crontab` anywhere (`grep -rn 'beat_schedule|crontab|periodic' apps/` → comments only).
2. **Job finalization has no safety net.** `finalize_jobs` is enqueued only by the spider pipeline post-commit (`libs/scrape-core/scrape_core/pipelines.py:376`); nothing invokes it periodically. Combined with #1: a job whose batch dies on a Scrapyd node before emitting any item stays `RUNNING` forever, its `scrape.job.*` webhook event never fires (`tasks_jobs.py:419-449`).
3. **Extraction chain is 3 of the 7 promised methods.** §16 orders platform pattern → JSON-LD → embedded JSON → CSS → XPath → regex → Playwright-rendered. Implemented: JSON-LD, CSS, regex (+ single-number heuristic): `_STRATEGIES = (extract_jsonld, extract_css, extract_regex)` in `libs/scrape-core/scrape_core/extraction/pipeline.py:38`. Platform patterns (Shopify `/products/<handle>.js`, Woo store API — §16 and `scrape_profiles.adapter_key` vocabulary §22), embedded JSON, and XPath exist only as enum values/confidence defaults (`libs/shared/app_shared/profiles/confidence.py:22-31`); an unrecognized preferred method is a no-op (`pipeline.py:51-65`). The browser project renders then reuses the same 3-method chain (`apps/scrapers-browser/.../generic_browser_price_spider.py:489-495`). DB columns for xpath/embedded-json config exist but are dead.
4. **Browser fallback is a per-profile mode, not a runtime escalation — and the terminal `PLAYWRIGHT_PROXY` plan is executed over plain HTTP.** §11's fallback chain ends "Attempt 4: Playwright through proxy". The access engine returns `PLAYWRIGHT_PROXY` as intent (`libs/shared/app_shared/access/engine.py:140-148`), but the HTTP spider's errback re-dispatches it through `self._dispatch` → `_request_for`, which builds a plain `scrapy.Request` (`apps/scrapers/price_monitor/spiders/generic_price_spider.py:288-296, 389-396, ~544`; verified the errback → `_dispatch(decision.plan)` path at lines 541-551). The attempt is recorded with `access_method=PLAYWRIGHT_PROXY` while actually fetched over HTTP — mislabeled rows feed `request_attempts` and the strategy-stats buffer (`pipelines.py:315-370`), poisoning optimizer learning. Browser execution only happens when `ScrapeProfile.mode = BROWSER` routes the whole batch at dispatch (`tasks_jobs.py:60-68, 261-280`). `specs/014-browser-scraping-service/spec.md:316` declares cross-job escalation out of scope (dangling).
5. **2 of 7 spec webhook event types unimplemented.** §22 lists `match.scrape.failed` and `product.comparison.updated`; neither exists (`grep -rn 'match.scrape.failed|product.comparison' apps/ libs/` → nothing; taxonomy at `libs/shared/app_shared/enums.py:545-552`). The other five (plus alert.resolved/reopened, job.partial_failed) are emitted from `tasks_analysis.py:388-426`, `tasks_jobs.py:419-449`, `tasks_strategy.py:697-748`.
6. **API surface vs §24 endpoint list** (beyond the deferred set above): `GET /v1/jobs` (list), `GET /v1/jobs/{id}/targets`, `/alerts`, `/attempts` are absent and never declared anywhere (008 promises only `/{id}` and `/{id}/results`, `specs/008.../spec.md:101-102`). The domain-strategy surface diverges from §24: implemented as `POST/GET /v1/strategy/discovery-runs` + `GET/PATCH /v1/strategy/profiles` (`routers/strategy.py:62-185`); `discover/competitor/{id}`, `discover/domain`, `POST .../rediscover`, `GET .../stats` do not exist (rediscovery is automatic-only via `rediscovery.py:435-490`; per-method stats have no read endpoint).
7. **Redis split (broker vs locks) missing.** §4 mandates two instances/configs, `noeviction` on the locks one, and says logical DBs are unacceptable. There is a single `REDIS_URL` (`libs/shared/app_shared/config.py:85`), one compose `redis` service with no `command`/`maxmemory-policy` (`docker-compose.yml:51-54`), and both Celery broker (`celery_app.py:54`) and lock/dedup/limiter client (`libs/shared/app_shared/redis_client.py:30`) use it. `specs/001-monorepo-skeleton/spec.md:21,126` deferred this as a "deployment concern" — never delivered (dangling).

## 3. RISKS

### 3a. SECURITY

- **S1 (Critical): RLS is ineffective in the shipped configuration.** The app connects as the Postgres superuser: `.env.example:14` (`DATABASE_URL=...crawmatic:crawmatic@pgbouncer...`) with `POSTGRES_USER=crawmatic` (`.env.example:89`, `docker-compose.yml:20`). Superusers bypass RLS even under `FORCE`. The intended `crawmatic_app` (no BYPASSRLS) and `crawmatic_auth` (BYPASSRLS) roles are documented only in `specs/003-auth-api-keys-workspace-isolation/quickstart.md:85-86`; no migration or script creates them (grep for `CREATE ROLE` across `alembic/` and `scripts/` → docs only). Every RLS policy in the schema is dead weight until an operator hand-provisions roles. Compounding: the CI lint that would catch unscoped queries is unwired and guards only 2 models (§2.2 item 10), so **both** isolation layers are currently advisory. Application-level `workspace_id` scoping in routers/repositories is the only live defense.
- **S2 (High): PgBouncer `AUTH_TYPE=trust` is the only shipped auth config** (`.env.example:93`; comment says deployed envs MUST use scram, but no deployed config exists — no railway/fly/Procfile manifests anywhere). §4 requires scram-sha-256 in every deployed environment.
- **S3 (Medium): No API-wide rate limiting and no generic exception handler.** Only login is rate-limited (`libs/shared/app_shared/security/rate_limit.py`, used solely at `routers/auth.py:104`). No `exception_handler`/`add_exception_handler` anywhere in `apps/api` (grep confirmed); unhandled errors fall through to Starlette defaults (no traceback body, but no sanitizing/logging middleware either). Authenticated bulk-upsert endpoints are unthrottled.
- **S4 (Low): Committed dev secrets in `.env.example`** — a real usable Fernet key (`:82`), `JWT_SECRET=change-me...` (`:48`), `SCRAPYD_PASSWORD=change-me` (`:34`). Labeled local-only; risk is copy-through to production.
- Positives worth stating: API keys SHA-256 + prefix + `hmac.compare_digest` (`security/api_keys.py:25-71`); refresh rotation is a single atomic UPDATE, reuse rejected (`security/tokens.py:23-30`, `routers/auth.py:163-164`); uniform login failure + dummy-verify timing (`routers/auth.py:128`); webhook secrets Fernet-encrypted with `key_version`, never echoed (`routers/webhooks.py:154-157`, `schemas/webhooks.py:128-173`); status cache cuts suspended workspaces within 30s (`security/status_cache.py:85`, `deps.py:174-224`); SSRF save-time + fetch-time both real (§2.3); Scrapyd basic auth baked (`apps/scrapers/docker-entrypoint.sh`, `scrapyd.conf`); non-root `USER app` in all six Dockerfiles.

### 3b. PERFORMANCE

- **P1 (High): No index on `match_current_prices(workspace_id, product_variant_id)`.** Only `ix_..._workspace_id` and the `(workspace_id, match_id)` unique exist (`alembic/versions/2db33dea5e14...py:178-191`). `recompute_variant` reads comparable rows per variant on every scrape completion and every client price change; at the spec's 10-20k matches/workspace (§39), each of the thousands of per-variant recomputes in a workspace job filters the whole workspace's current-price set.
- **P2 (Medium): No index on `scrape_job_targets(scrape_job_id, status)`** (`a6b0234cd4ad...py:88-107`; the `(scrape_job_id, match_id)` unique gives only a job-prefix). `finalize_jobs`/`recover_stalled_batches` filter by job+status; and `finalize_jobs` re-scans **every** non-terminal job on each invocation (`tasks_jobs.py:345-449`) while being enqueued once per pipeline flush per job — O(active jobs × flushes).
- **P3 (Medium): `GET /v1/jobs/{id}/results` is unpaginated** (`apps/api/app/routers/jobs.py:93-116`) — returns all targets; a workspace-scope job is 10-20k rows in one response. `GET /v1/api-keys` also unpaginated (`routers/api_keys.py:101-122`; low volume).
- **P4 (Low): Reactor/pooler hygiene is otherwise strong** — batched flushes, `prepare_threshold=None` on all engines (`database.py:63,137,214`), capped pools (`DB_POOL_SIZE=5/+2`), no `time.sleep` on the reactor (grep verified), buffered stats and throttled `last_used_at`. Note the auth/system engines don't set pool caps (`database.py:130,207`) — they use SQLAlchemy defaults (5+10 overflow), which slightly loosens the §4 connection budget.

### 3c. ARCHITECTURE

- **A1 (Critical): No periodic trigger for stall recovery + no finalize safety net** (§2.2 items 1-2). Violates §26 node-loss handling and success criterion 33. A single Scrapyd node death (or a lost dispatch task, see A2) leaves jobs permanently `RUNNING`, targets `PENDING`, with no webhook and no operator signal. The fix is ~5 lines in the existing scheduler accumulator pattern (`scheduler_app.py:218-240`).
- **A2 (High): No Celery `acks_late`, no retries, on a broker-shared Redis.** Grep across `apps/workers` for `acks_late|autoretry|max_retries|self.retry` → nothing. Default early-ack means a worker crash mid-`dispatch_job`/`recompute_variant`/`create_webhook_event` silently drops the task; the design compensates with idempotency + watchdogs, but the watchdog isn't scheduled (A1). Result: task loss is currently unrecoverable for dispatch (until A1 is fixed) and permanent for webhook events (fire-and-forget, `tasks_analysis.py:419-426`).
- **A3 (High): Single Redis instance for broker + correctness-critical state** violates §4's explicit two-instance rule (evidence in §2.2 item 7). A broker backlog can OOM/evict the instance holding dispatch-idempotency guards, in-flight locks, and rate-limit state; spec calls evictions on the locks instance "an incident". Restart-window safety (fencing tokens, NX guards, unique constraints) is implemented, but eviction-under-pressure is not bounded like a restart.
- **A4 (Medium): `PLAYWRIGHT_PROXY` mislabeling corrupts the optimizer's inputs** (§2.2 item 4) — violates principle 9's fallback semantics and undermines §14 learning (browser-attempt stats are actually HTTP results).
- **A5 (Medium): Missing webhook event types** `match.scrape.failed` / `product.comparison.updated` (§22) narrow the integration contract the spec promises plugins.
- **A6 (Medium): Zero CI** — single-head migration guard and workspace-scoping lint exist but nothing runs them; §22 and §32 both explicitly require CI enforcement.
- **A7 (Low): Duplicated `parse()` bodies** between the two spiders (`generic_price_spider.py:398-484` vs `generic_browser_price_spider.py:458-539`) — the exact drift §5 built `scrape-core` to prevent; `SKIPPED` targets drop their `error_code` (`LOCKED_ALREADY_RUNNING` unrecorded — documented gap at `pipelines.py:269-278`, hurts §34 error-code reporting).

### 3d. OPERATIONAL COST

- **O1 (Medium): The scheduler process is the single heartbeat for everything periodic** — refresh rules, partition creation, retention, rollups, stats flush, light re-check all ride one loop (`scheduler_app.py:218-240`). It's stateless and multi-instance-safe for the refresh pass (SKIP LOCKED), but if it's down, retention/partition-creation silently stop (1-month partition lookahead, `config.py:239`, gives a grace window). No liveness metric exists to notice.
- **O2 (Medium): Observability is JSON-log-lines only.** No Prometheus/StatsD/OTel/Sentry anywhere (grep verified); the only structured emitter is opt-in `scrape_core/observability.py:38`. Of §31's monitoring list, pgbouncer saturation, Redis memory/evictions, queue depth, and Scrapyd node liveness have no signal at all — and `max_client_conn` is unset in the PgBouncer config, so the §4 connection budget is neither configured nor observable.
- **O3 (Medium): Proxy budget and rate ceilings fail open on Redis errors** (`libs/shared/app_shared/access/budget.py:11-17,51-75`) while the token bucket fails closed — a Redis outage removes the monthly proxy spend cap exactly when retries spike. Deliberate divergence, but it's an unbounded-egress-cost path.
- **O4 (Low): Fixed 24/7 footprint** — 8 always-on containers including the Chromium-baked browser node (`max_proc=1`, `apps/scrapers-browser/scrapyd.conf`) even for workspaces with zero BROWSER profiles. Storage growth is genuinely controlled (partition drop wired, O(months) partitions). Redis keyspace (locks, dedup `analysis:enqueued:*` TTL 6h `config.py:154`, stats buffers with PEXPIRE) is TTL-bounded.

## 4. FUTURE / AT-SCALE CONCERNS (all FUTURE — not launch blockers)

- **FUTURE — Cross-workspace domain rate fairness:** limiter keys are `rate:{workspace_id}:{domain}:{method}` (`limiter/keys.py:21`), exactly as §12 specifies — but N workspaces matching the same competitor domain each get the full per-domain budget, so the target site sees N× the intended rate. Needs a global per-domain cap layer before many workspaces share popular competitors.
- **FUTURE — `finalize_jobs`/`light_recheck`/`flush_stats` scan breadth:** finalize scans all non-terminal jobs across all workspaces per invocation (`tasks_jobs.py:187-203` unscoped ref scan); light-recheck patrols 200 profiles/60s (`tasks_strategy.py:103`). Fine for tens of workspaces; needs sharding/cursoring at hundreds.
- **FUTURE — Single shared `maintenance` queue** carries eight task types (`celery_app.py:120-129`); a slow retention drop can delay stats flushes and stall recovery. Split queues or add priorities as volume grows.
- **FUTURE — Scheduler claim loop is one-rule-per-transaction** (`refresh.py:94-106`, limit 100/pass, 30s poll) — thousands of rules due at the same minute (daily-midnight herd) will smear firing over multiple passes.
- **FUTURE — Webhook fanout:** v1 is poll-only with keyset pagination and a supporting index (`03dec3037c8f...py:133-142`) — fine. When the delivery worker lands, per-event × per-endpoint fanout, retry storage, and delivery-time SSRF re-validation all need design (nothing exists — see 2.1).
- **FUTURE — Scrapyd horizontal limits:** pools + blake2b domain sharding are ready (`jobs/nodes.py:16-38`), but Scrapyd itself is single-node/non-durable-queue; per-node queue-depth/liveness monitoring (§31) is unbuilt.
- **FUTURE — Partition count** (4 tables × 12/yr) and UUIDv7 index locality are non-issues for years.

## 5. TOP URGENT PRE-DEPLOYMENT ITEMS (ranked)

1. **Provision the non-superuser DB roles and repoint `DATABASE_URL`/`AUTH_DATABASE_URL`** (add a migration or bootstrap script for `crawmatic_app`/`crawmatic_auth` per `specs/003.../quickstart.md:85-86`), and set PgBouncer to scram — otherwise RLS, the project's central isolation guarantee, is inert (S1, S2).
2. **Wire `SCRAPE_RECOVER_STALLED` (and a periodic `SCRAPE_FINALIZE_JOBS` sweep) into the scheduler loop** — one more accumulator in `scheduler_app.py`; without it, any node loss or dropped dispatch task strands jobs forever (A1).
3. **Set `task_acks_late=True` (+ `task_reject_on_worker_lost`) or add explicit retries** for `scrape_dispatch`/`price_analysis`/`webhook_events` — every task is already idempotent, so late-ack is safe and closes the silent-loss window (A2).
4. **Split Redis (broker vs `noeviction` locks/limits) or at minimum pin `maxmemory-policy noeviction` + memory alerting on the single instance** — §4 calls evictions on lock state an incident (A3).
5. **Fix the `PLAYWRIGHT_PROXY` terminal-plan path in the HTTP spider** — either terminal-fail with a `PLAYWRIGHT_FAILED`-style code or actually re-dispatch to the browser pool; today it fetches over HTTP and writes mislabeled attempt/strategy rows (A4).
6. **Add the two missing composite indexes** — `match_current_prices(workspace_id, product_variant_id)` and `scrape_job_targets(scrape_job_id, status)` (P1, P2) — plus pagination on `GET /v1/jobs/{id}/results` (P3).
7. **Stand up minimal CI**: run `scripts/check_single_head.sh`, `scripts/check_workspace_scoping.py` (and widen its model list), and the unit suite on every push — two spec-mandated guards currently enforce nothing (A6).
8. **Close the operator-visibility gap for launch**: `GET /v1/jobs` list + `/targets`/`/attempts` (or equivalents) and basic queue/scheduler liveness signals — with jobs only fetchable by ID and no metrics, a stuck pipeline is invisible from the API (O1, O2, §2.2 item 6).

Items 1-3 are the true blockers: they are cheap fixes to already-built machinery, and each currently negates a §2 non-negotiable (27, 22/§26-recovery, and the §4 Redis rule respectively).
