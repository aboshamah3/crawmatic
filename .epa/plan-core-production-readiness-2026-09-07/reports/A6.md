## Deviations
1. **`price_ok` join** — the packet says join `request_attempts.success AND price IS NOT NULL` as `price_ok`. `request_attempts` has no `price` column (price lives on `price_observations`, keyed by `match_id`/`scrape_job_id`, with no reliable 1:1 join to one operation). `request_attempts.success` is already the terminal price-extraction outcome per its own model docstring (FR-013: one row per attempted target, `success=False` on e.g. `PRICE_NOT_FOUND`/`EXTRACTION_FAILED`, not merely transport failure) — the same field this repo's own diagnostic SQL (`evidence/cost-performance-2026-09-07/followup_probes.py:35`, precedent from the deep-dive author) aliases `price_success`. I used `a.success` alone via `network_request_id`/`network_operation_id` and dropped the extra `price IS NOT NULL` join as an unreliable, schema-unsupported addition. Impact: MINOR — no test asserts the SQL text; the pure `summarize()` calculator (the tested surface) takes `price_ok` as a pre-computed boolean regardless of how the caller derives it.
2. **`strategy_profile_id`** — no column of that name exists anywhere in the schema (verified: `request_attempts.scrape_profile_id`, `domain_strategy_profile_id` on strategy tables). Realized the "resolved profile" dimension as `request_attempts.scrape_profile_id` (the actual column recording which profile a fetch ran under) in `load_phase_dimensions`/`evaluate_coverage`'s `*_strategy_profile_id` parameters. Impact: MINOR — internal metric naming only, not exercised by C3's spend run in this environment.
3. **"> 5% unknowns" formula** — not given a concrete formula in the packet. Defined `unknown_pct = 100 * (unknown_durations + unknown_bytes) / max(pages, 1)` in `evaluate_coverage`, normalizing both duration-unknowns (parent-scoped) and bytes-unknowns (row-scoped) against the page count. Documented in the function's docstring. Impact: MINOR — reversible, internal to this script, not exercised until C3 (deferred, no spend).
