## Deviations

1. **`refresh_rule_occurrences` is a Core `Table`, not an ORM model (MINOR).** `app_shared.models.base.Base` mints a surrogate UUIDv7 `id` primary key on every subclass (FR-003). The plan's DDL makes `(rule_id, scheduled_for)` the primary key, and that composite IS the guarantee — a surrogate key would demote the uniqueness that carries the whole thing to a secondary constraint. Declaring the table directly against the shared `metadata` keeps the plan's exact DDL while staying inside Alembic autogenerate/offline render and the naming convention. No other table in this repo does this; if the reviewer prefers a `Base` subclass, the alternative is a surrogate `id` plus `UniqueConstraint(rule_id, scheduled_for)`, which raises the same `IntegrityError` but is not the DDL the plan specifies.

2. **`2**n × 60 s` reads `n` as the post-increment `consecutive_failures` (MINOR).** So the first failure backs off 120 s, the second 240 s, and the 6 h cap binds from the ninth. The other reading (`n` = prior failures, first backoff 60 s) is equally defensible; the literal one was chosen because the criterion sets `consecutive_failures` and then names `n` in the same breath. Pinned by `test_failure_backoff_is_exponential_and_capped_at_six_hours` so a change would be deliberate. Low-impact and reversible: one constant.

3. **The backoff helpers live in `refresh.py`, not `scheduler_app.py` (MINOR).** Both the fair pass and the legacy loop need them, and `scheduler_app` already imports `refresh`; putting them in `scheduler_app` would have made `refresh` import it back. `scheduler_app` imports `record_rule_failure`/`clear_rule_failures` from `refresh`.

4. **`tests/unit/test_refresh_pass_isolation.py` was rewritten, not extended (MINOR, and the reviewer should read it).** It asserted the pre-B3 contract *verbatim* — "`session_factory` is invoked exactly twice: claim A, claim poison, stop" — which is the `break` this task removes. Its fake session also ignored the claim predicate entirely, so it could not have observed a backed-off rule leaving the due window. It now evaluates `enabled`/`next_run_at <= now` off the real statement and asserts the inverse property: a rule ordered AFTER the poison one fires in the SAME pass. Every other assertion it made (rollback isolation, untouched clock fields, bounded call count, no spin) is preserved.

## Notes for reviewer

- **FLEET-WIDE BEHAVIOUR CHANGE, made deliberately: `SCHEDULER_FAIR_QUEUE_ENABLED` now defaults to `True`.** This is an explicit plan decision, not a deviation. From the next scheduler deploy, `run_fair_scheduling_pass` — not `run_refresh_pass` — is what fires due rules in production. It orders by freshness urgency, admits under the fleet/domain concurrency caps (`SCHEDULER_FAIR_QUEUE_DOMAIN_CONCURRENCY` = 4, `..._FLEET_CONCURRENCY` = 64) and weighted fair share, calls C3's non-spending entitlement check per candidate, and dead-letters a rule (disables it + emits `scheduler.item.dead_lettered`) after `SCHEDULER_FAIR_QUEUE_MAX_ATTEMPTS` = 3 consecutive faults. Prod sets every flag NULL today, so the code default rules. **The first thing to watch after deploy is the `scheduler: fair pass candidates=… dispatched=… denied=… deferred=…` line**: a large `denied` means entitlement evidence is stale, a large `deferred` means the domain cap is biting. Rollback is one environment variable (`SCHEDULER_FAIR_QUEUE_ENABLED=false`), and the fallback path got the same per-rule isolation in this task, so rolling back no longer costs the isolation fix.
- **The two guards are complementary, and the tests defeat them separately.** The recheck alone still loses to clock skew or a long pause between the two statements; the occurrence key alone turns every stale candidate into a wasted INSERT-and-rollback. `test_a_stale_candidate_is_refused_without_creating_anything` defeats the recheck outright (winds the rule's clock back to an occurrence already recorded) and asserts the primary key alone still holds.
- **Second-precision truncation is load-bearing.** `occurrence_key` drops microseconds, so a microsecond of clock or round-trip drift between replicas cannot mint two "distinct" occurrences for one firing. Cron rules and interval rules both derive `next_run_at` at second granularity or coarser, so nothing is lost.
- **The occurrence row survives a zero-match scope.** `create_scope_job` returns `(None, None)` when a scope resolves to no ACTIVE matches (FR-015); the occurrence is still claimed with a NULL `scrape_job_id`, because it still happened. Leaving it unclaimed would let every subsequent pass re-attempt the same empty occurrence indefinitely.
- **Riskiest untested path: the durable backoff under a real concurrent load.** `record_rule_failure` takes its own `FOR UPDATE SKIP LOCKED` on the rule in a fresh transaction; if a *second* pass holds that row at that instant the lock is skipped, the write is silently dropped and the rule stays due (it is retried next tick, with the in-process ledger still counting). That is the conservative failure mode — never a lost job, never a double backoff — but it is asserted only against fakes, not against real concurrency the way the occurrence claim is.
- **B2's follow-up is closed**: `reconcile_inflight_intents` now has a Celery task (`maintenance.reconcile_dispatch_intents`), a `maintenance` route, a 300 s time limit, and the DURABLE `dispatch_reconcile` cadence (5 min, its own knob). Durable deliberately — the rows it settles exist because a worker died, and an in-process accumulator resets on exactly that event. `tests/unit/test_dispatch_reconcile_schedule.py` asserts all four, including that it is not the fifth member of the registered-but-unrouted set B4 flagged.
- **B4's pre-existing routing gap is unchanged** (`COSTAUTH_RESERVATION_SWEEP`, `MAINTENANCE_RECONCILE_PROVIDER_USAGE`, `MAINTENANCE_COST_ROLLUP`, `MAINTENANCE_ENTITLEMENT_REFRESH` have `time_limit`s but no `task_routes` entry, so they land on the unconsumed default queue). Still out of scope here; still worth someone's attention.

At the plan's own retention defaults it is the obvious next candidate — it is not partitioned, so it would need a plain age-based `DELETE`, which is fine for a table with no partitions.
