## Deviations
1. **Escalation-ladder hook placement (CONTEXT.md unknown 3).** `scrape_core/strategy/escalation.py` does not exist, as CONTEXT.md said. The budget is consulted in `app_shared/strategy/methods.py`, inside the candidate loop of the resolver that every physical attempt goes through — `resolve_next_physical_attempt`, with `resolve_method_candidate` now a thin `.selection` wrapper over it so no existing caller changes. `resolution.py` was deliberately **left untouched**: `resolve_strategy_start` decides *where the ladder starts*, not *whether an attempt may happen*, and putting a Redis-backed gate in a documented-pure function that runs once per group (not per attempt) would gate the wrong thing and would widen the C4 merge surface for no gain.
2. **Two files edited that the packet's Scope list does not name**, both required by the acceptance criteria:
   - `libs/scrape-core/scrape_core/errors.py` for the new classification helpers. It is *the* failure-classification module; the alternative (classifiers in `attempt_budget.py` or `targets.py`) would have put them somewhere no future reader looks.
   - `libs/shared/app_shared/opsmetrics/emit.py` + `tests/unit/test_ops_metrics_baseline.py` for `crawmatic_attempt_budget_exhausted_24h`, which the criteria name explicitly. The A5 test file hard-codes the gauge count (7 → 8), so it had to move with it.
   Also `task_names.py`, `celery_app.py` and `tasks_maintenance.py`, which the packet's own task-specific note requires ("register the new Celery task's time limit consistent with B4's annotations").
3. **`AttemptBudget` is typed into the ladder as a Protocol, not imported.** `tests/unit/test_import_boundaries.py::test_app_shared_does_not_depend_on_scrape_core` is a *textual* scan — it fails on the literal string `scrape_core` anywhere under `app_shared/`, comments included. So `app_shared` code refers to it only as "the scraping runtime's attempt-budget gate". This caught a real first-cut violation; the boundary now holds.
4. **`try_consume` charges at resolution, not at fetch.** A caller that resolves a method and then fails to dispatch has still consumed the intent, and a budget charged only on success cannot bound a method that reliably crashes. Documented on `resolve_next_physical_attempt`.
5. **Redis failure is fail-OPEN** (matching the `defer_budget` precedent). Reasoning is in the module docstring and pinned by two tests: every verdict here becomes *persisted evidence* in `request_attempts.error_code`, and fabricating `ATTEMPT_BUDGET_EXHAUSTED` out of a Redis blip would poison the strategy optimizer and the domain scorecard for every target at once. The bound that actually caps spend — the wall-clock deadline — is pure arithmetic and holds with Redis down (`test_redis_outage_does_not_lift_the_deadline`).

Deviation impact: MINOR

- **Wiring is deliberately partial and that is the remaining work.** This packet delivers the budget, the ladder hook, the classes and the tuner.
