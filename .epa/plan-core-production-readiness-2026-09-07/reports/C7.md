## Deviations

1. **Files outside the Scope list.** All listed above. Each is forced:
   - *ORM model + `models/__init__.py`* — a new table absent from `Base.metadata` is invisible to Alembic autogenerate and to `target_metadata`; `rollup_watermarks` sets the exact precedent (declare the model, do all runtime I/O through raw `text()` behind a `to_regclass` probe).
   - *`rls_table_manifest.txt` / `grants_expected.yaml` / `provision_db_roles.sql`* — this is the defect the B10 rehearsal found: a new table missing from these three ships unreadable and unwritable by every application role, and `tests/integration/test_tenant_isolation_roles.py::test_catalog_matches_reviewed_manifest` fails. Classified SYSTEM; `crawmatic_app` gets DELETE/INSERT/SELECT (no UPDATE — the fleet-table rule), `crawmatic_auth` all four (the system session does the upsert), `crawmatic_scraper` nothing — identical to `rollup_watermarks`.
   - *`config.py`* — the batch size and the invocation budget must be operator-tunable, not constants. Added append-only in a delimited block as the slot instruction required.
   - *`tasks_maintenance.py`* — "re-enqueue until `complete`" is an explicit acceptance criterion and the task is where it lives.
   - *The three existing test suites + `_rollup_batch_fake.py`* — their fake sessions dispatched on the rendered SQL of the three statement builders this task removes. They could not have kept passing. The new shared fake evaluates the real statement's own bind parameters over in-memory rows, so "idempotent"/"no double count"/"a crash before commit discards the batch" remain *observed* properties.
   - *`test_migration_offline_rollup_completion.py`* — the repo's standard guard for every new revision.
2. **The batch statement is one `INSERT ... SELECT` wrapped in a data-modifying CTE.** The packet says "renders one `INSERT ... SELECT`"; it does (exactly one, asserted). The wrapping `WITH upserted AS (INSERT ... RETURNING ...) SELECT ...` is what returns the four things the driver needs — pairs covered, rows written, variants with no client state, and the keyset cursor — as a projection of the *same* snapshot as the write, in one round trip. Issuing them separately would re-scan the day's partition per batch and could disagree with what the INSERT did.
3. **`gen_random_uuid()` for the surrogate `id`.** A set-based insert cannot call `app_shared.ids.new_uuid7`. Same trade-off already made by `6e4a9c8f2d10`'s `INSERT ... SELECT` backfills and `price_observations.attempt_uuid`'s server default. Sound because `id` is a pure surrogate: identity is `(workspace_id, product_variant_id, date)`, which is the upsert's conflict arbiter, and nothing reads these rows in id order.
4. **`run_daily_rollup` now commits per batch, so `run_rollup_catchup`'s final batch commits just *before* the watermark advance rather than with it.** The no-loss/no-double-count property is unchanged and is now enforced twice: a crash in that gap leaves the day's rows durable and the watermark un-advanced, so the day is re-planned — and its `rollup_completion` row already says `complete`, so the re-plan is a no-op that just advances the cursor. Documented in the function.
5. **`test_each_day_commits_separately_so_progress_is_durable_mid_batch` changed from `commits == 3` to a property assertion.** A three-day catch-up now commits twice per day. The test asserts the thing that actually matters — every day's rows, cursor and checkpoint durable, nothing pending — instead of a transaction count that was only ever a proxy for it.
6. **`aggregate_competitor_prices` is no longer on the live path.** It is kept, updated to the new semantics, and documented as the executable specification the integration test hand-computes against. Calling it per pair *was* the N+1.

## Notes for reviewer

- **C8 reads `rollup_completion.complete`.** One row per UTC day; `TRUE` only when a batch ran off the end of the day. An **absent** row and an **incomplete** row both mean "do not assume this day is finished" — the migration seeds nothing, deliberately, because inventing `complete=TRUE` for days this code never verified would authorise a partition drop on a lie. `read_completion(session, day)` is the accessor.
- **Semantic change is user-visible.** `average_competitor_price` and `comparable_competitor_count` will change value for any variant whose competitors were scraped at differing frequencies. `comparable_competitor_count` now counts *competitors*, not readings. Historical rows are not rewritten; `recompute_window` re-derives a range under the new rule if that is wanted.
- **Untested path:** the re-enqueue itself (`_reenqueue_daily_rollup`) is best-effort and swallows exceptions — it needs a live broker to exercise. The correctness mechanism is the durable cursor, not the enqueue; a failed enqueue costs latency until the next scheduler tick, never data.
- **Rows with `match_id IS NULL` cannot occur** (`price_observations.match_id` is NOT NULL), so the SQL has no null-match branch. `aggregate_competitor_prices` does handle `match_id=None` — each such row is its own group, never merged — because it is a public pure function that callers may hand partial rows.
- **Documentation drift, not fixed (out of scope):** `specs/015-retention-rollups-partition-maintenance/contracts/daily-rollup.md` still describes the per-pair loop *and* the pre-M3 `scraped_at::date = D` predicate — it was already stale before this task. `tests/load/scenario_n1_detection.py` (B7, marker `load`) targets exactly the N+1 this task removed; its `else` branch already reports "No N+1 signature detected", so it will now pass through that path, but its prose still describes the finding as unfixed.
- **Benchmark asserts the shape, not just the clock:** statement count must be `<= 2 * batches + 2` and `< VARIANTS`. A fast machine can hide an N+1; that assertion cannot.
