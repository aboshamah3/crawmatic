## Deviations

1. **Scraper settings path.** The packet names `apps/scrapers-http/price_monitor/settings.py`; that directory does not exist. The HTTP scraper lives at `apps/scrapers/price_monitor/settings.py`, which is what was edited (the browser path was as given).
2. **`spool.resolve(ids)` is called by the pipeline, not inside `_flush_batch`.** The acceptance sentence is ambiguous about the caller, but the plan's own `test_flush_failure_defers_and_replays_once` monkeypatches `_flush_batch` with a stub that never resolves and still asserts `pending_count() == 0`, so resolution must live in the pipeline's success callback. `_flush_batch` still takes `spool_ids` (per the named signature) and uses it in the new `persistence.flush` log line.
3. **Test mechanism for the two named unit tests.** The plan sketches a live reactor + a `run_reactor_until` helper. Implemented with the seams this suite already uses for reactor code — a synchronous `run_in_thread` stand-in and an injected `twisted.internet.task.Clock` — so the assertions are the plan's (`calls == [2, 2]`, `pending_count() == 0`, a third `process_item` returning an unfired `Deferred`) while the tests stay deterministic and never sleep through a 600 s backoff. `BatchedPersistencePipeline` gained a `clock=` kwarg for that (default: the installed reactor, imported at call time, never at module import — the existing reactor-mismatch rule).
4. **Backpressure Deferreds fire on flush *completion*, not only on success.** Literal "resolved on the next successful flush" would wedge the spider permanently during a database outage: items stop being pulled, so no flush can ever succeed and `close_spider` never completes. Capacity genuinely is free after a failure (the batch is back in the spool awaiting `callLater`, not in `_pending`). Documented at the call site.
5. **Two files outside the packet's file list were modified, both entailed by the acceptance criteria**: `libs/shared/app_shared/models/observations.py` (the new `price_observations.attempt_uuid` column + both `UniqueConstraint`s — the migration cannot be used without them) and four existing test files (see Files changed) whose ORM-`add_all` assumptions the required `ON CONFLICT DO NOTHING` change invalidates.
6. **`attempt_uuid`/`scraped_at` are stamped in `process_item`, before spooling.** The identity the ON CONFLICT arbiter uses must be stable across a replay; minting it at flush time (as `_flush_batch` did for attempts) would generate a fresh UUID per replay and defeat the whole mechanism. `_flush_batch` keeps its fallback for direct callers.
7. **`_CLOSE_FLUSH_GRACE_SECONDS = 30.0` is a module constant, not a `Settings` knob** — the plan lists exactly four new settings and this is a shutdown grace period, not a per-deployment tuning decision. Nothing is lost when it expires; the results stay spooled and `open_spider` replays them.

## Notes for reviewer

- **Riskiest change: `session.add_all` → Core `pg_insert(...).on_conflict_do_nothing()` for observations and attempts.** `_row_values` lowers each ORM instance to an insert dict and resolves the Python-side column defaults Core would otherwise skip (`id` → `new_uuid7()`, `attempt_number` → 1, `terminal_for_target` → True, `origin` → SCRAPE); columns that are `None` and carry only a *server* default are omitted so PostgreSQL fills them, and a batch whose rows disagree on such a key is refused rather than written. Only `request_attempts.attempt_uuid` is server-default-only, and it is always supplied. Worth a second pair of eyes.
- **The migration rewrites `price_observations`** (volatile ADD COLUMN default) and takes ACCESS EXCLUSIVE for the two unique indexes. A bulk `UPDATE` backfill was deliberately NOT used: both tables carry `FORCE ROW LEVEL SECURITY`, so a migration-time UPDATE with no `app.workspace_id` set would match zero rows and silently backfill nothing. Rationale is in the revision docstring, including the staged alternative for a table too large for the lock.
- **`crawmatic_persistence_quarantined_batches`**: this repo has no Prometheus client in the spider process, and `opsmetrics` renders DB-derived snapshots — which a quarantined batch by definition never reached. Implemented as a module-level counter in `pipelines.py` + `crawler.stats.inc_value(...)` when a crawler is present + a `persistence.quarantined` structured log line. `rules.py` was not touched (PB-8 owns it), and no threshold was added there.
- **Untested at runtime**: `open_spider`'s replay against a real spider (unit-tested with a fake seam), the reactor `callLater` path with the real reactor (Clock-tested), and the spool directory creation (`/var/lib/crawmatic/spool/`) inside a container — the deploy must mount a writable volume for `SCRAPE_RESULT_SPOOL_PATH`, on the same volume as `NETLEDGER_BUFFER_PATH`, or `ResultSpool.__init__` will raise at pipeline construction. That is the same failure mode the netledger buffer already has, but it is new surface for the scrapers.
- **Follow-up worth tracking**: nothing drains `kind='quarantined'` rows. They accumulate on disk until an operator acts. A future task could expose a count via the ops endpoint or add an admin drain command.
