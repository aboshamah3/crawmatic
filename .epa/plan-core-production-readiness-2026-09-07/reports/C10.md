## Deviations

1. **`scripts/dr/backup_prod.sh` keeps the legacy dump path as an automatic fallback** (`--mode auto`, the default: pull if `/root/.crawmatic-dr/pull.env` exists, else dump + four WARN lines). The plan says it "becomes the pull side". Provisioning `dr-backup` is a deferred owner gate, and the host's cron runs this script every 4 h — deleting the dump path on merge would leave production with **no backups at all** until the gate is taken. The fallback is loud on every run and named as temporary in the RUNBOOK.
2. **`pyproject.toml` (repo root) gained `exclude = ["apps/dr-backup"]`** — outside this packet's declared file scope, added on the orchestrator's instruction because `apps/*` claimed the new directory and broke every `uv run` (including `check_single_head.sh`). Chosen over adding a member `pyproject.toml` because the exclude leaves `uv.lock` untouched (the lock is root-owned and a new member would have rewritten it).
3. **`railway.json` carries `volumes` and an `x-crawmatic` metadata block.** The packet asks for the volume in `railway.json`; Railway's schema does not officially define volumes there, so it is declared *and* the CLI/dashboard equivalent is written out in RUNBOOK §7 step 1.
4. **The Railway volume/cron conflict is resolved by documentation plus a code path, not by a second service.** A Railway volume attaches to exactly one service and a cron service is not running between invocations, so the cron shape and the file server cannot both own `/backups` as separate services. `railway.json` keeps the cron shape the packet specifies, and `serve.py` gained a ~15-line in-process scheduler (`$DR_SCHEDULE_LOOP=1`) so the owner can instead run one always-on service that both serves and backs up. Both shapes are written out in RUNBOOK §7 step 1.
5. **`dr_dump_target` moved from `backup_prod.sh` into `dr_lib.sh`.** Not asked for, but the alternative was two copies of the dump/manifest logic (host + container) that would drift, and a drill that passes on one writer's sets and fails on the other's.

## Notes for reviewer

- **The egress guarantee is enforced in three places**: `backup.sh` dies on a non-private `PGHOST`; `backup_prod.sh` refuses plain HTTP to a non-private host; `test_dr_backup_script_lint.py` fails if either guard, or a public hostname literal, appears. That triple is deliberate — the property is invisible until a bill arrives.
- **The BLOCKERS.md 2026-09-08 B2-fix1 follow-up is closed in this task** as far as this packet's scope allows: RUNBOOK §5 "Replaying the migration chain onto an empty database — the RLS no-op trap" documents all five latent migrations, why they are harmless in production and lossy on a fresh replay, and the three-option procedure (restore the dump; or replay with `BYPASSRLS` granted and immediately revoked; then verify the backfills landed). `verify_restore.sh` pins the known set in `DR_RLS_BACKFILL_KNOWN` and **fails the drill if it grows**, so a new migration of that shape cannot land unnoticed. `rehearse_upgrade.sh` was left alone — it is outside this packet's file scope.
- The audit parses migrations with Python's `ast`, not grep, specifically so `b6e5d1c94a72`'s docstring — which explains at length why a bare `UPDATE dispatch_intents` would be wrong — is not reported as the bug it warns about. Verified: the scan returns exactly the five known migrations and does not flag `b6e5d1c94a72`.
- **Untested paths**: the actual Railway deployment (deferred gate); `dr_load_pgenv`'s Railway-CLI branch in `--mode dump` (unchanged by this task, and running it means a production `pg_dump`); the pull loop end-to-end against a live `serve.py` (its two halves are tested separately — `serve.py` over loopback with curl, and the pull's URL/checksum guards by lint — because exercising the whole loop locally would have meant weakening the `*.railway.internal` guard or editing `/etc/hosts`).
- `bytes_on_wire` in the smoke run (766 KB for a 4 KB dump) is the container's whole-namespace counter including connection setup; at production dump sizes it is dominated by the dump and is the right order of magnitude. It is a *delta of a kernel counter*, deliberately not "bytes pg_dump wrote" — that number is `bytes_exported`, and recording both is the point.
- The engine `alembic_head` recorded in a set is read inside the dump's own snapshot; the SaaS database has no `alembic_version` (Prisma-migrated) and records `"none"`, which the drill passes explicitly rather than skipping.
