## The grants gap (C8's finding, fixed)

My work hit it: `run_retention` and `create_missing_partitions` both fail as `crawmatic_auth` on a correctly provisioned database, because creating or reclaiming a partition requires OWNERSHIP of the parent and `provision_db_roles.sql` §8 (correctly) moves ownership to `crawmatic_migrate`. §8's own text promises that "the maintenance job's partition creation is granted explicitly rather than by making a runtime role the owner" and then grants nothing.

Fixed in `scripts/provision_db_roles.sql` as a new §9: two SECURITY DEFINER functions, `crawmatic_create_partition(parent, child, from, to)` and `crawmatic_drop_partition(child)`, owned by `crawmatic_migrate`, `EXECUTE` granted only to `crawmatic_auth`, `search_path` pinned, `PUBLIC` revoked first. Neither is a general DDL hole: create requires the parent to already be `relkind = 'p'` and the child to be `<parent>_YYYY_MM`; reclaim requires the target to currently BE a partition (absent = no-op, preserving FR-020 idempotence).

Two further things the fix had to include, each found by running it:
1. **Grants.** A partition does not inherit its parent's ACL, and privileges are checked on the relation a query NAMES. Ordinary reads name the parent, but retention's own coverage gate scans the CHILD by name — so the create function copies the parent's `relacl` (via `aclexplode`) onto the new child. Before the seam this was hidden because the runtime-created child happened to be owned by the role that needed to read it.
2. **RLS.** `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` and `CREATE POLICY` are also owner-only, so `PARTITION_RLS_INHERITANCE_SQL` could not run on the maintenance session either. The create function now applies the parent's posture (enable + force + copy policies) to the child inside the same privileged call, and `create_missing_partitions` issues the schema-wide statement only on the fallback path. Both are idempotent and produce the same result.

`app_shared.maintenance.partitions` probes for the functions with `to_regprocedure` and routes through them only when present; the probe is total (any failure reads as "no seam"), so every database provisioned before §9 and every unit-test fake keeps the old direct-DDL behaviour. Proven both ways: `tests/unit/test_partition_seam.py` covers the fallback and the seam paths, and verification §5 above ran the whole retention/partition suite as `crawmatic_auth` on an ownership-adopted database.

## Deviations

1. **`config.py` was not purely append-only.** `RETENTION_PRICE_OBSERVATIONS_DAYS` changed 90 → 180 in place (one literal, plus a comment). The acceptance criterion demands 180; the alternative — re-declaring the field inside the append block — would leave two contradictory declarations of one knob in one class, which pydantic resolves silently by last-wins. Every genuinely new setting went in the delimited block as instructed. Impact: MINOR.
2. **Table names.** The criteria name `cost_settlements`, `RETENTION_COST_ALLOCATIONS_DAYS` and `RETENTION_COSTAUTH_RESERVATIONS_DAYS`; this schema calls those tables `network_operation_settlements`, `network_operation_allocations` and `cost_reservations`. The SETTING names ship exactly as specified; the registry maps each to the real table, and `ledger_summaries.SETTLEMENT_TABLE` documents the correspondence. Impact: NONE.
3. **Five foreign keys dropped — the material consequence of the swap.** A foreign key must reference a UNIQUE constraint and a partitioned table's unique constraint must include the partition key, so `network_operations`' identity key became `(network_request_id, created_at)` and these could not survive: both self-references, `network_operation_allocations.operation_id`, `network_operation_settlements.operation_id`, `request_attempts.network_operation_id`. Two things are genuinely weaker: `network_request_id` is unique per MONTH rather than globally (a caller-minted UUIDv7, so collision is not a practical risk, but it is no longer forbidden), and a referencing row can outlive the operation it names. `ledger_summaries.find_orphan_references` is the scheduled, read-only stand-in. See Escalation. Impact: MATERIAL.
4. **`run_retention` now gates on `RETENTION_ENABLED_CLASSES`, which ships EMPTY — so on a default deployment retention drops and deletes nothing at all.** This is the conservative reading of "NOTHING drops until the owner lists the class" and is fail-closed (data is retained, never lost), but it does turn off retention for the four families that were live before this task until the owner ratifies. Impact: MATERIAL (behaviour), fail-safe direction.
5. **New Part C in `run_retention`** — bounded batched row retention for the `ROW_DELETE` families. Not literally in the criteria, but a registry of families nothing sweeps is a dead registry. `cost_allocations` batches by `operation_id` because `trg_noa_allocation_total` is a DEFERRED trigger checking a whole operation's allocations at COMMIT; a batch boundary inside a set would read as a shortfall and abort the pass. Impact: MINOR.
6. **The swap does NOT drop the legacy table.** It survives as `network_operations_pre_partition` (registered GAP with zero privileges for every application role). Dropping it is an owner step and the only rollback that does not require re-copying. Impact: MINOR (disk).
7. **The Celery/scheduler wiring for `MAINTENANCE_LEDGER_SUMMARIZE_CHILDREN`** was added (task name, cadence key, scheduler entry, task, route, time limit). A task nothing can enqueue is not a task, and `tests/unit/test_celery_time_limits.py` fails without the limits. Impact: MINOR.

Deviation impact: MATERIAL

## Escalation

**Owner decision required BEFORE the swap is run against production** (the swap is already an owner-run step; this is what should be ratified with it):

> Partitioning `network_operations` by `created_at` makes `network_request_id` unique per month rather than globally, and removes the five foreign keys listed in Deviation 3. Re-establishing them would require denormalising the parent's `created_at` onto four tables, one of which (`request_attempts`) is itself a partitioned hot path. The alternative is to keep the ledger unpartitioned and accept a bulk `DELETE` for its retention, which FR-015/SC-003 forbid. Accept the trade, or direct a different design.

Also, though not blocking: **the retention numbers and the partition-swap trade both need the owner's signature** on the `Ratified by owner on ____` lines in `docs/RETENTION_POLICY.md` before any class is added to `RETENTION_ENABLED_CLASSES`. Nothing is deleted until then, deliberately.
