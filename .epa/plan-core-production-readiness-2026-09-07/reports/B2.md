## Deviations
1. **The migration adds only what was missing.** B1's `e7b21f3a8c94` already created `state`, `posted_at` and `confirmed_at`, so this revision adds `node_url` and retypes `scrapyd_job_id`. `RECONCILED_MISSING` needs no DDL — `DispatchIntentState` is an app-validated `VARCHAR(32)`, never a Postgres ENUM, which is this repo's convention for every status column.
2. **No `kind` column on `outbox_messages`.** The acceptance text says `outbox_messages(kind='job_created', payload={job_id})` and "`outbox/dispatcher.py` handles the new kind". The table has no `kind` column and the drain is deliberately generic (it publishes `payload` verbatim as the task's kwargs and knows nothing about any task). The kind is therefore expressed as `task_name=SCRAPE_DISPATCH_JOB` + `dedup_key="job_created:<job_id>"`, which produces exactly the required behaviour (`SCRAPE_DISPATCH_JOB` enqueued from the drain) with no consumer-side routing table to keep in sync. Documented in `outbox/dispatcher.py`.
3. **The outbox change covers all three job-creation seams**, not only `create_scope_job`: `create_match_job` and `create_variant_job` shared the same `_enqueue_dispatch` helper, and the criterion is "every direct `.delay()`-before-commit call site is removed". `grep -rn "\.delay("` over `apps/`+`libs/` now finds no call sites. Manual job dispatch gains up to `OUTBOX_DRAIN_INTERVAL_SECONDS` (5 s) of latency.
4. **`reconcile_inflight_intents` writes `RECONCILED_MISSING`; B3's in-dispatch `reconcile_inflight` still writes `PLANNED` on absence.** Both mean "looked, not there"; `InflightReconciliation.may_repost` now accepts either. The re-POST carries the same id in both cases because the id lives on the row, not on the attempt.
5. **Cost authorization is reserved in the plan pass** (per the criterion), so a two-batch job whose first POST fails now releases *two* grants — the failing batch's, and the batch the pass never reached — instead of one. `tests/unit/test_jobs_dispatch_task.py`'s expectation was updated and now also asserts the two releases are distinct ids.
6. **Files touched outside the packet's list**, all necessary and none owned by a sibling: `enums.py`, `models/dispatch.py`, `scrapyd/reconcile.py`, `jobs/service.py` (this is where `create_scope_job` lives), and the six test files listed above that my schema/behaviour change broke.

## Notes for reviewer
- **Intended commit message:** `feat(dispatch): commit-before-send intents with stable Scrapyd job ids; outbox for job-created (F06)`
- **The five steps, as implemented in `dispatch_job`:** (1) route + `_skip_unsupported_batch` + `authorize_or_none` + `intents.plan(..., node_url=)` + `target.claimed_at`, then one `session.commit()` — which also closes the task's transaction; (2)/(3) `client.schedule(..., jobid=)`, whose `record_post` commits through the store's own short transaction *before* the POST and leaves the outer session idle during it; (4) `confirm` (again the store's own transaction) then `stamp_targets_dispatched` + `remote_accepted_at` + `session.commit()` per batch; (5) any death after (2) leaves a committed `POSTED` row for `reconcile_inflight_intents`.
- **The riskiest change is the `scrapyd_job_id` retype.** It changes the column's *meaning* from "what the node answered" to "the name we chose and POSTed". A node that ignores the `jobid` field still has its answer adopted when it parses as a UUID (Scrapyd 1.6 mints `uuid1().hex`, which does); a non-UUID answer is logged and the planned id kept. The backfill takes `intent_id` for any row without a UUID-shaped value — deterministic, unique, and exactly what the pre-B2 `SCRAPYD_DETERMINISTIC_JOBID` path would have POSTed for that row.
- **`ScrapydDispatchClient.list_jobs` raises rather than returning an empty set on an unreachable node.** That asymmetry (contrast `daemon_status`, which returns `None`) is load-bearing: an empty set authorizes a re-POST, so a network failure must never produce one.
- **Untested path:** `recover_stalled_batches` still uses the caller-owned store (it is a FLEET sweep with its own long transaction and is edited by B3/B6 in later waves). It now records `node_url` and POSTs the deterministic jobid, so its rows are reconcilable, but it does not yet run the committed-before-POST protocol. Follow-up if the reviewer wants full parity.
- **Nothing schedules `reconcile_inflight_intents` yet.** It is a library function with no Celery task or beat entry — a deliberate stop, since adding a maintenance task means touching `scheduler_app.py`'s beat loop and `task_names.py`, which B3/B6 own in later waves. Wiring it is the natural follow-up.
- `DispatchIntentStore(session_factory=...)`'s factory contract is "returns a context manager yielding a session that can already see these rows" — the same seam shape `drain_outbox` uses. Scoping is the injector's job (`_intent_session_factory` sets the GUC; the sweep would inject the BYPASSRLS system sessionmaker).
