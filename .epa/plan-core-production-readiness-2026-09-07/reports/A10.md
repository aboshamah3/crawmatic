## Deviations
1. **The rehearsal script provisions roles/grants TWICE (before AND after `alembic upgrade head`), not once, and this is now what §2.6 of the release doc mandates for the real deploy too.** The plan's step 6/7 ordering (provision, then migrate) is necessary for the *role* half (crawmatic_migrate must exist before alembic can authenticate as it) but insufficient for the *grants* half: `provision_db_roles.sql` section 5's own comment documents that a manifest table not yet existing in the database is "skipped with a WARNING rather than aborting". The first real rehearsal run proved this is not theoretical — `control_plane_rules` (created by migration `b7c1d2e3f4a5`→`c8d2e3f4a5b6`) came out of `alembic upgrade head` with zero grants, and `verify_grants.py` correctly FAILed with 4 MISSING findings. `provision_db_roles.sql` is fully idempotent by design, so the fix is a second, free invocation after the migration — implemented in the script and carried into the release doc as §2.6's mandatory two-pass sequence. Impact: MATERIAL (changes the deploy-day command sequence from what the plan's literal step 6→7 text implies), but it is a strict addition (one more idempotent command), not a change to what any single command does, and it is the only way `verify_grants.py` can pass at all after a from-zero provision+migrate.
2. **The rehearsal script also performs a FUNCTION-ownership adoption step that `provision_db_roles.sql` itself does not have.** `provision_db_roles.sql` section 8 ("adopt ownership") reassigns only `TABLE`/`SEQUENCE` ownership into `crawmatic_migrate`; it has no equivalent for `FUNCTION`/trigger-function ownership. The first rehearsal run failed `alembic upgrade head` with `InsufficientPrivilege: must be owner of function network_operation_allocations_check_total` for exactly this reason (a fresh restore leaves every function owned by whichever role ran `pg_restore`). The script fixes this **only inside its own throwaway database** (an explicit, separately-timed, loudly-commented step — never a silent workaround) since `provision_db_roles.sql` is out of A10's file scope to modify. Whether real production hits the same wall depends on whether `crawmatic_migrate` already owns every function a pending migration touches there, which is unknown from this sandbox — the release doc's §2.6 therefore adds a mandatory, read-only pre-flight query for this before the real migrate step, plus the one-line `ALTER FUNCTION ... OWNER TO crawmatic_migrate;` fix if it's needed. Impact: MATERIAL (a previously-undocumented, evidence-based gap in the shipped provisioning script, now flagged for its owner — A3 — as a follow-up to extend section 8), but zero change to any existing file: the workaround is entirely inside the new script, and the release doc treats it as a pre-flight check, never an assumption that production is already fine.
3. **Postgres major used for the rehearsal is 18 (`postgres:18-alpine`), never the compose-pinned 17.5.** Required by the packet, not a deviation from it, but recorded here because it means `scripts/dr/rehearse_upgrade.sh` never touches `docker compose`'s own `postgres` service at all (compose is pinned to a stale major) — it starts and tears down its own throwaway container every run, sized to whatever the backup manifest's `server_version` field says. `docker-compose.yml`'s pin is flagged as a tiny separate follow-up (out of A10's file scope: "Create docs/ops/RELEASE_1_2026-09.md, scripts/dr/rehearse_upgrade.sh. Modify nothing else.") in both the script's header comment and the release doc §1 Finding 1.
4. **Roles/scripts run as `mahmoud` via `sudo -u mahmoud -E`, not as root, for the provision/alembic/preflight/verify_grants steps**, even though the script as a whole must run as root (needed for `$DR_KEY_FILE`, mode 600 root-owned). Only the gpg-decrypt/restore step needs root; every subsequent step is an ordinary network connection to the throwaway container and follows the repo's stated convention of running engine commands as `mahmoud`. Required a `$WORK/mahmoud` subdirectory (`chown mahmoud:mahmoud`, `chmod 700`) with the parent `$WORK` at `711` (traversal-only for mahmoud, no listing) so `preflight_regex_profiles.py`'s `--report` file can be written by `mahmoud` without granting it any visibility into the root-owned gpg/pg_restore stderr captures alongside it. Low-impact, reversible, not escalated.
5. **The release doc's §2.10 (20-target S-Tech smoke) documents a read-only SQL query to FIND a qualifying variant and a scoped ledger-link-fraction query, rather than pointing at a pre-existing "run N targets" script — none exists.** Jobs are created per-match or per-variant (`POST /v1/jobs/run/match/{id}` / `POST /v1/jobs/run/variant/{id}`, `apps/api/app/routers/jobs.py`); there is no batch endpoint. `stech.ink` is confirmed as the platform's direct (non-proxied) canary domain from `alembic/versions/d9a46612bcc8_domain_playbooks_state.py`'s `_ACTIVE_SEED_DOMAINS`.
