## Deviations

1. **`load_targets` uses the batch sibling `mark_targets_started`, not N × `mark_target`.** The
   plan's step 2 writes the pickup as `mark_target(..., only_if_status=(PENDING, DEFERRED))`, which
   is one statement *per match*. `load_targets` is a documented bounded load whose whole design
   invariant is "one query for the batch, never one per match" (Principle IV) — a per-target
   statement there would land on the hottest path in the engine. `mark_target` still gains
   `only_if_status` and the timestamp kwargs and still issues exactly the specified single
   `UPDATE ... SET status='STARTED', started_at=COALESCE(started_at, now()) WHERE status IN (...)`
   (directly asserted, statement-count included, in
   `test_mark_target_only_if_status_issues_exactly_one_conditional_update`); the batch form is the
   same statement with `match_id IN (...)`. Behaviour is identical; only the statement count differs.
2. **Two model files outside the packet's file list were modified**:
   `libs/shared/app_shared/models/jobs.py` and `.../models/observations.py`. Unavoidable — the
   acceptance criteria require the pipeline to *persist* the new columns, which cannot happen
   without the ORM mappings. The edits are additive column declarations matching the migration
   exactly (asserted by `test_scrape_job_targets_table_has_the_new_phase_columns` and by the
   information_schema check above).
3. **`tests/unit/test_pipeline_target_terminalization.py` was edited.** Its `mark_target` double
   had a closed signature and rejected the new phase kwargs. The change is confined to the doubles
   (`**phases` capture + a `_RecordingStampTimestamps` stand-in); every existing assertion is
   untouched and all 12 of its tests pass.
4. **`rules.py` carries the thresholds; `emit.py` re-exports them.** The plan lists both files.
   Rather than duplicate five numbers across two modules (drift bait), the constants live once in
   `rules.py` — the judgement half of the trio — and are imported into `emit.py` (no cycle: `rules`
   never imports `emit`). They are module constants, not `Thresholds` fields, because
   `Rule.evaluate` takes an `OpsSnapshot` and `BaselineMetrics` deliberately is not one; adding
   unevaluated fields to `DEFAULT_THRESHOLDS` would claim coverage that does not exist. B9 promotes
   them when it wires the collection into the snapshot.
5. **SQL the plan did not specify was authored for three gauges** (`persistence_failures_1h`,
   `queue_oldest_pending_seconds`, `target_phase_p95_seconds`) — the plan excerpt gives SQL for the
   other four only. Definitions, each documented at its constant:
   - `persistence_failures_1h` — attempts in the last hour with `success IS TRUE` and **no**
     `price_observations` row for that `(workspace_id, match_id)` in the window. Money spent, page
     fetched, nothing durable out of it. Scoped to successes on purpose: counting failed fetches
     would drown the signal.
   - `queue_oldest_pending_seconds` — `EXTRACT(EPOCH FROM now() - MIN(created_at))` over `PENDING`
     targets; deliberately the same shape as the existing
     `crawmatic_target_oldest_age_seconds{status="PENDING"}` so the two can never disagree.
   - `target_phase_p95_seconds` — `created_at→dispatched_at`, `dispatched_at→first_network_at`,
     `first_network_at→persisted_at`, each `FILTER`ed to rows where both boundaries are non-NULL.

## Notes for reviewer

- **Intended commit message** (the orchestrator commits, per the packet):
  `feat(jobs): targets really become STARTED; per-phase timestamps; baseline freshness/amplification metrics (deep dive §5)`
- **The pickup is placed after the match load, not after the terminal filter.** Two reasons, both
  deliberate: only match_ids that actually resolved in-workspace are claimed (claiming a match_id
  that does not exist would be a lie), and it leaves `test_load_targets_terminal_skip.py`'s
  statement-order assertions — which count the terminal probe and the matches query — exactly as
  they were. Still inside the same `workspace_txn`, so the "same transaction" criterion holds.
- **`attempt_uuid` ADD COLUMN rewrites `request_attempts`.** A *volatile* default
  (`gen_random_uuid()`) cannot be stored as metadata, so every monthly partition is rewritten under
  `ACCESS EXCLUSIVE`. Bounded by the 90-day retention window and this repo's migrations run as a
  one-shot job with no concurrent writer, so it is acceptable — but it is the one operationally
  sharp edge in the revision and the migration's docstring spells out the staged alternative (add
  NULL → backfill per partition → `SET DEFAULT` → `SET NOT NULL`) if a future deployment's table
  makes the lock matter. **Worth an operator's eye before the production migrate job runs.**
- **Untested paths.** Plan step 3 also assigns `claimed_at`/`remote_accepted_at` to
  `tasks_jobs.dispatch_job` and the spider-side sourcing of `first_network_at` from
  `request.meta["download_slot_start"]` / Playwright `request.timing["requestStart"]`. Those write
  sites are **not** wired here — the plan hands them to B2 ("B2 keeps these") and the spiders are
  outside this packet's file scope. The columns, the single writer, the transport field on
  `ScrapeResult` and the persistence seam all exist and are tested; what a reviewer should expect is
  that until B2 lands, `claimed_at`/`remote_accepted_at` stay NULL in production and the
  `dispatch_to_first_network` p95 has no samples unless a spider populates
  `ScrapeResult.first_network_at`. That is honest NULL-means-not-measured behaviour, not a silent
  zero — the metric SQL filters those rows out.
- **`mark_target` stamps phase timestamps *before* the terminal guard**, on purpose: "the document
  arrived at T" stays true for a target another attempt has already terminalized, and refusing to
  record it would lose the only evidence of where the time went. It is still not a transition — the
  status guard is untouched.
- `LedgerCoverage`/A7's block in `emit.py` was extended around, never replaced.
