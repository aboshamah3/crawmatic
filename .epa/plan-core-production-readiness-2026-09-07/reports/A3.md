## Deviations
Three material, evidence-based deviations from the packet's literal text, plus one real bug found and fixed during verification:

1. **`crawmatic_auth` keeps SELECT+INSERT+UPDATE on `network_operations`** (packet said "no SELECT network_operations"). `libs/shared/app_shared/netledger/recorder.py`'s open/close/replay path (`_apply_close`, `_write_child`, lines ~697/757/785) runs on `get_system_session()` (== crawmatic_auth) and issues real `SELECT ... FROM network_operations` statements as part of the idempotent-close guarantee, plus the INSERT (open) and UPDATE (close). Revoking SELECT here — `recorder.py` is out of this packet's file scope — would break every ledger close, i.e. the C1/C3 cost-accrual pipeline, in production.
2. **`crawmatic_app` keeps SELECT (only) on `network_operations`** (packet said tenant roles should read only `workspace_usage_v`, never the table). `apps/api/app/services/admin_usage.py` (line ~252, `noqa: workspace-scope`) joins `NetworkOperation` directly on the ordinary `crawmatic_app` session for the admin usage-report endpoint. INSERT/UPDATE/DELETE were still removed from `crawmatic_app` on this table (no writer via that role was found anywhere in the tree), closing 3 of the 4 privileges the table's own GAP annotation in `rls_table_manifest.txt` names as residual exposure.
3. **`crawmatic_scraper` is created by `provision_db_roles.sql` section 3a, not by the Alembic migration** (packet named the migration file `..._tenant_usage_view_and_scraper_role.py` and its acceptance criteria say the migration creates the role). `provision_db_roles.sql`'s own header already documents "WHY THIS IS NOT AN ALEMBIC MIGRATION" for the other three roles: `crawmatic_migrate` — the role Alembic authenticates as in production via `MIGRATION_DATABASE_URL` — is provisioned `NOSUPERUSER` with no `CREATEROLE`; a migration running `CREATE ROLE` would fail with a permission error against a real production deployment (it would only appear to work in a test/compose environment where migrations happen to run as the database owner, which is exactly how the compose-based integration test above did NOT catch this — it was found by re-reading the SQL file's own documented rationale, not by a failing test). The migration creates only the view; the role and its full grant set come from `provision_db_roles.sql`, matching the other three roles' lifecycle.
4. **Bug found and fixed during verification, not a deviation from the packet**: my first pass at section 5's REVOKE+GRANT loops applied privileges to base/parent table names only. `tests/integration/test_tenant_isolation_roles.py` immediately caught it — `crawmatic_app` lost all access to the MONTHLY PARTITION CHILDREN of `request_attempts`/`price_observations`/`price_alert_events`/`webhook_events` (a direct `SELECT * FROM webhook_events_2026_09` raised `InsufficientPrivilege`), because the old blanket `GRANT ... ON ALL TABLES IN SCHEMA public` had enumerated each partition individually while my explicit per-table loop did not. Fixed by having every REVOKE/GRANT loop also iterate `pg_inherits` children of the named table (mirroring the existing `PARTITION_RLS_INHERITANCE_SQL` pattern for policies) before applying the privilege set. Also fixed a separate plpgsql syntax bug in the same pass: `FOREACH tbl IN ARRAY[...]` needs the literal `ARRAY` keyword twice (`FOREACH tbl IN ARRAY ARRAY[...]`), which the file's own pre-existing section 8 already did correctly and my new code initially did not.
