## Deviations

1. **Table name: `scrape_profiles`, not `strategy_profiles`** (impact: the one that matters).
   No table named `strategy_profiles` exists. The two candidates are
   `scrape_profiles` (owns every `*_regex` column; what the preflight script
   enumerates) and `domain_strategy_profiles` (learned per-domain access/extraction
   start; carries **no** regex at all). The quarantine is about a stored pattern, so
   it is on the row that stores the pattern. Recorded here rather than escalated
   because only one reading is implementable at all.
2. **`REGEX_TIMEOUT` is signalled through a ContextVar, not a return value.**
   The acceptance text says `extract_regex` returns `None` *and* the caller records
   `REGEX_TIMEOUT`. Those two cannot both be true without a side channel: the
   deadline fires four layers below the classification site
   (`extract_regex` → `pipeline.extract` → `adapters/html.adapt` → spider `parse`),
   and all three intermediate signatures are public API pinned by their own tests.
   `regex_deadline_watch()` / `regex_deadline_tripped()` scope the signal so it
   cannot leak between pages; the spider reads it immediately after `adapt()`.
3. **Enforcement of the quarantine is at the extraction seam, not the resolver.**
   "The profile resolver skips the regex strategy for quarantined profiles":
   `apps/api/app/services/profile_resolution.py` resolves profile *ids* and never
   sees strategies, so a skip there would be a no-op. The skip lives in
   `extract_regex` (`_regex_quarantined`), which every extraction path — default
   chain, ranked path, HTTP and browser spiders — funnels through. Fails **open**
   on a profile lacking the attribute, so a pre-migration row is never blinded.
4. **Files touched beyond the packet's scope list**, both required by acceptance
   criteria the listed files cannot satisfy: `apps/scrapers/price_monitor/spiders/generic_price_spider.py`
   (the "caller" that records the error code) and `libs/scrape-core/scrape_core/pipelines.py`
   (the "pipeline" that increments the counter). Also `apps/api/app/schemas/admin.py`
   (response model for the new route, per repo convention that `app_shared` never
   imports pydantic) and `libs/shared/pyproject.toml` (the probe needs the engine).
   The browser spider was deliberately **not** touched — it is held by A1/A9 work.
5. **Two existing tests updated**, both invalidated by changes the task mandates:
   - `tests/unit/test_regex_live_path_bounds.py` patched module constants that the
     task explicitly promotes to `Settings`; it now patches the `_bounds_*` accessors.
   - `tests/unit/test_models_control_plane.py::test_alembic_reports_exactly_one_head_and_it_is_this_revision`
     asserted the head *is* `c8d2e3f4a5b6`, i.e. "no migration may ever land after
     mine". Renamed and rewritten to assert the real invariant (exactly one head,
     and `c8d2e3f4a5b6` still on the path to it).
6. **Settings reads are fail-soft.** `get_settings()` cannot be constructed in the
   unit suite (`tests/conftest.py` supplies a deliberately incomplete environment;
   `.env` has no `JWT_SECRET`/`ENCRYPTION_KEYS`/`SCRAPYD_*`). A raising settings read
   inside a text-node loop would have cost 30 pre-existing tests. Each site falls
   back to the value shipped in `Settings` (`_DEFAULTS` in the extraction module,
   `_DEFAULT_MAX_PATTERN_CHARS` in validation, `3` in the repository); every real
   process validates config at startup, so the fallback never decides anything in
   production.
7. **`old_price_regex`/`currency_regex` are outside the preflight sweep** — the task
   names `price_regex`/`stock_regex` only. All four are covered at write time and at
   runtime; only the release-gate sweep is narrower.

## Notes for reviewer

- **Intended commit message**: `feat(extraction): regex engine with hard deadline, pattern caps, profile quarantine (F02)`
- **The `regex` engine is not equivalent to `re`.** It is stricter on a few
  constructs, so `compile_regex_or_reject` now compiles on *both* and refuses a
  pattern the execution engine rejects — otherwise such a profile would silently
  find nothing on every page forever. No stored production pattern is affected
  (all four shapes from the W5.5-L1 scan are covered by
  `test_real_price_patterns_pass_every_gate` and by the untouched
  `test_extract_regex_unchanged_for_the_stored_production_patterns`).
- **The probe catches what the static screen cannot.** `(a|aa)+c` is exponential and
  invisible to the overlapping-alternation heuristic (which only fires on
  *textually identical* branches). `test_the_probe_only_pattern_really_does_escape_the_static_screen`
  guards that this stays true, so the probe test cannot silently stop testing the probe.
- **Global profiles are never auto-quarantined.** `record_regex_timeout` scopes its
  UPDATE to `workspace_id = :ws`, so a `workspace_id IS NULL` row cannot have its
  behaviour changed from inside one tenant. Releasing (and, if ever needed,
  quarantining) a global row is operator-only via the admin route, which is
  cross-workspace by construction. This is the conservative reading of "workspace-scoped
  UPDATE"; if the intent was for a bad *global* regex to self-contain, that needs a
  decision and a system-sweep seam.
- **Untested paths**: the admin route and the pipeline counting block have no unit
  test that drives a real session (both need a live DB — integration territory).
  The UPDATE statement shape *is* pinned offline
  (`test_record_regex_timeout_is_workspace_scoped_and_atomic`), and the route was
  smoke-checked for registration only. Worth an integration test in a later phase.
- **Per-page budget semantics**: `4 x timeout` is *cumulative CPU across nodes for one
  pattern*, measured with `time.monotonic()` around each `search`. A profile with four
  regex rules can therefore spend up to `4 x 4 x timeout` = 4 s at the default on a
  pathological page before every rule has given up. That is bounded and non-catastrophic,
  but it is 4 s, not 1 s — worth knowing when tuning `EXTRACTION_REGEX_TIMEOUT_SECONDS`.
- **A10 release checklist**: `scripts/preflight_regex_profiles.py --report out.json`
  should be added to it. It reads `PREFLIGHT_DATABASE_URL` (falling back to
  `DATABASE_URL`), is read-only, and must be pointed at a restored dump or staging —
  it deliberately burns the deadline per offending pattern.
