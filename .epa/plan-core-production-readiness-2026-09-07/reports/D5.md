## Deviations

1. **`queue_oldest_seconds_p95` and `persistence_lag_seconds_p95` are read from `scrape_job_targets`' existing three-phase lifecycle p95 (`created_at`→`dispatched_at`→`first_network_at`→`persisted_at`), not from a genuine percentile of a live "oldest pending" gauge sampled repeatedly across the day.** No time-series sample store exists anywhere in this codebase to p95 a point-in-time gauge over a day — `queue_oldest_pending_seconds` (`app_shared.opsmetrics.emit`) is a single instantaneous number, not a distribution. `queue_oldest_seconds_p95` therefore reads the `due_to_dispatch` phase p95 (how long a target waited in queue before dispatch, p95 over the day's targets) and `persistence_lag_seconds_p95` reads `first_network_to_persisted` (an exact naming match, no substitution). Documented at length in the module docstring. Reversible and low-risk (a scorecard display metric, not a billing or gate figure). Impact: MINOR.
2. **`browser_share`/`proxied_share` are computed over TOP-LEVEL `network_operations` rows only (`parent_operation_id IS NULL`)**, not C6's full parent+child join — a fleet-wide daily MIX gauge, not a billing figure, and children inherit their parent's transport/provider by construction rather than needing an independent decision this gauge re-examines. Kept to one straightforward statement rather than reusing C6's multi-CTE per-tenant export shape. Impact: MINOR.
3. **`railway_cpu_seconds`/`railway_ram_gb_hours`/`railway_egress_gb` are always `NULL`.** Checked (as instructed) whether "the existing watchdog's stored output" exists: `app_shared.memory_watchdog` enforces a live RSS ceiling and persists nothing durable anywhere. No Railway API call was made (forbidden by the packet). Documented via `RAILWAY_METRICS_UNAVAILABLE_REASON`; a future importer (Railway usage-export shape, like `scripts/import_dataimpulse_usage.py`) is the named follow-up. Impact: NONE (this was explicitly anticipated and permitted by the packet).
4. **`backup_egress_gb` is fed by a Redis hash, not a second table.** The packet caps this stage at one Alembic revision, so `POST /admin/ops/backup-report` folds accepted reports into a per-UTC-day Redis hash (atomic `HINCRBY`, 45-day TTL) rather than a durable table of its own; `compute_scorecard` reads it once when assembling a day's row. If Redis is down or a day received no report, the field is `NULL` (not `0`); if a day received only private-network legs, it is a measured `0.0` (the C10 success case). This is a genuinely new piece of state outside the packet's literal file list, but it is the direct mechanism the packet's own "Open item" asked for ("Add the receiver... so backup freshness becomes a scorecard input"). Impact: MINOR (Redis unavailability degrades this one field to `NULL`, nothing else).
5. **`tests/unit/test_migration_offline_network_operations_partition.py` was modified** — outside this packet's file scope, at the orchestrator's explicit instruction after PD-2 flagged the one cross-packet unit failure this migration caused (a test that pinned `a5e0c74b13d9` as *the* current head verbatim). Fixed to assert the property that actually matters (one head; the swap revision still in history) rather than "the swap is the newest migration". Impact: NONE (test-only, makes the assertion correct going forward instead of newest-migration-fragile).
6. **`GET /admin/scorecard`'s `until` is today UTC, not yesterday.** Today's row is simply absent (not yet written) rather than special-cased out of the range — the same "an absent row says nothing was measured yet" discipline the table itself follows. Impact: NONE (read-only, matches the acceptance's literal `?days=30` shape).
