## Deviations
1. **The placement coordinator lives in `app_shared.jobs.node_load` (`NodePlacement`), not as a private class in `tasks_jobs.py`.** `tasks_jobs.py` keeps only a five-line `_node_placement()` factory that supplies the lazy probe client. Reason: `apps/api` and `apps/workers` both ship a top-level `app` package, so importing `app.workers.tasks_jobs` in the shared unit process is ambiguous — every existing dispatch test pays for that with a subprocess harness. Putting the policy in `app_shared` makes it directly unit-testable and leaves `tasks_jobs.py` with wiring only. Behaviour at both call sites is exactly what the packet specifies.
2. **A totally unreachable pool still re-POSTs on the stall-recovery path** (`NodePlacement(unreachable_pool_fallback=True)` -> `select_node`), while the primary dispatch path defers as specified. Applying "unreachable == saturated -> defer" literally in `recover_stalled_batches` deletes the reaper's reason to exist: F-2's contract is "every node this suite reaps is DEAD, so re-dispatch must proceed", and a dead pool would otherwise permanently suppress the one sweep that moves work off dead nodes (it broke 9 of `test_jobs_stall_recovery.py`'s tests). A pool with a reachable-but-FULL node still defers there — that is a genuine capacity answer. The re-POST is free if the pool really is gone: it fails, and the existing failure path releases the C3 grant immediately. Covered by `test_a_totally_unreachable_pool_defers_on_the_dispatch_path`, `test_a_totally_unreachable_pool_still_re_posts_on_the_recovery_path`, `test_the_recovery_fallback_does_not_apply_to_a_reachable_but_full_pool`.
3. **A single-node pool short-circuits to `select_node` and is never probed**, per the criterion "`select_node` is kept for the single-node case only". Consequence: on today's deployments (one URL per pool) B6 changes no runtime behaviour at all — no `daemonstatus.json` probe, no Redis key, no `ScrapydDispatchClient` constructed for probing, and no batch can be deferred. The capacity rule activates the moment a second node is added to `SCRAPYD_*_URLS`.
4. **One file touched outside the packet's list**: `libs/shared/app_shared/jobs/dispatch_intents.py`, for the `planned_node_url` read (six lines + docstring, no write path, no schema). Without it "a retry reads `intent.node_url`" has no accessor. Not a file any sibling owns.
5. **`choose_node` raises `ValueError` on an empty pool** rather than returning `None`. A missing `SCRAPYD_*_URLS` is a misconfiguration; collapsing it into `None` would make it indistinguishable from a busy fleet and silently defer every batch forever. Matches `select_node`'s existing behaviour.
6. **`reserve_node` is a small addition to the packet's API list.** Without it a pass that places four batches against one 10-second-old snapshot places all four on the same node, and the "spread" criterion cannot hold. It is pure (returns a new dict).

## Notes for reviewer
- **Intended commit message:** `feat(dispatch): load-aware node placement persisted on the intent; bounded scrapyd queues (F11)`
- **Deviation 2 is the one judgement call in this task.** If the reviewer wants the literal reading (a dead pool defers stall recovery too), the change is one keyword: drop `unreachable_pool_fallback=True` at `tasks_jobs.py`'s `recover_stalled_batches` placement — and 9 tests in `tests/unit/test_jobs_stall_recovery.py` then need their F-2 expectations rewritten.
- **`SCRAPYD_MAX_PENDING_PER_NODE` bounds `pending`, not `running`.** A node with 9 running spiders and an empty queue is still eligible; `max_proc` is what bounds concurrency (`scrapyd.conf`, unchanged: 1 browser / 8 HTTP). The two knobs are independent by design, which `test_max_pending_bounds_pending_only_a_busy_node_is_still_eligible` pins.
- **The negative cache TTL (60 s) is a correctness property, not a tuning knob** — `read_node_loads` ignores the caller's `ttl` for an unreachable node. This is what makes "treated as saturated for 60 s" true rather than "for one call", and it stops a dead node being re-probed (and re-timed-out) by every dispatch pass.
- **Redis is a cache and only a cache here.** Every `get`/`set` is wrapped; a Redis outage degrades to "probe every pass" (`test_a_redis_outage_degrades_to_probing_every_time`). The one thing it cannot do is invent capacity: a failed *probe* is always `NodeLoad(reachable=False)`, never `NodeLoad()`.
- **Untested path:** the multi-node placement has no end-to-end test through `dispatch_job` itself (the deferral is proven at `NodePlacement.place`, and the call site is a plain `if node_url is None: continue` before the C3 gate). Every existing `dispatch_job` test uses a single-node pool, and adding a multi-node one means a new subprocess harness; `test_jobs_stall_recovery.py`'s 3-node HTTP pool does exercise the multi-node path end to end on the recovery side.
- **Not wired:** nothing exports a metric for deferrals. `NodePlacement.deferred` counts them per pass and each is logged at INFO with domain + mode; an ops counter is the natural follow-up if F11 wants a dashboard.
- **The first full-suite run of this task hung** (>65 min, sleeping in `ep_poll`, 53 s CPU) while the parallel sibling's suite ran concurrently; it was killed. The clean re-run above (582 s, exit 0) was done with no other suite running. No hang was reproducible in any single file, and nothing this task adds performs an unbounded wait — but if the reviewer sees the same symptom under parallel load, it is worth a second look rather than a retry.
