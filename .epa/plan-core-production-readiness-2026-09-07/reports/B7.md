## Deviations

1. **`apps/api/app/abuse_limit.py` was NOT converted to `redis.asyncio.Redis`.**
   Deviation impact: MATERIAL — flagging for owner/architect attention,
   not blocking the rest of B7.
   The acceptance criteria and plan excerpt both say "`rate_limit.py`
   and `abuse_limit.py` hold no synchronous `redis.Redis`... use
   `redis.asyncio.Redis`... one Lua script for atomic INCR+EXPIRE." As
   written today, `abuse_limit.py` holds **no Redis client of any
   kind** — it is Postgres-authoritative and explicitly, deliberately
   **fail-closed** (a prior task, "EPA W5.5-L1 item 2", per its own
   module docstring lines 1-47). That docstring argues at length,
   specifically against Redis for this module: *"Redis... is a cache in
   this system and a cache never grants — a counter an attacker can
   evict is a counter an attacker can reset."* Converting it to Redis
   (even async, even with atomic INCR+EXPIRE) would regress it from
   fail-closed to fail-open-under-a-Redis-blip for the abuse-prevention
   surface — a genuine security regression on a surface whose whole
   point is resisting an attacker who can *cause* store failures. I
   read this as the plan's B7 text pre-dating (or simply not accounting
   for) that later redesign, and picked the conservative, non-regressing
   reading: leave `abuse_limit.py`'s storage as-is. The acceptance
   criterion's literal text ("holds no synchronous `redis.Redis`") is
   trivially satisfied since it holds none at all. I did not
   full-ESCALATE and halt B7 over this since the rest of the task is
   unambiguous and independently valuable; this paragraph **is** the
   escalation for this one point — please have an owner/architect
   confirm the abuse_limit.py Postgres-authoritative design is intended
   to stand, or explicitly override it.

2. **"Authenticated quotas are keyed by workspace"** is implemented for
   JWT principals only (a signature-verified `decode_access_token` call,
   no DB/Redis round trip) — API-key credentials (`ck_...`) keep the
   pre-F15 per-credential-hash bucket. Deviation impact: MINOR.
   Resolving an API key's real workspace requires the full DB-backed
   lookup in `app.deps._authenticate_api_key` (prefix lookup + hash
   verify against every candidate row); duplicating that in middleware,
   on every request, purely for admission control would (a) add a
   mandatory DB round trip to a path that's supposed to be
   *non-blocking and cheap*, and (b) create a second, divergence-prone
   place that verifies API-key credentials. The chosen behavior is
   strictly *more* restrictive, never less: several keys in one
   workspace get separate budgets instead of pooling one, which cannot
   let a workspace exceed what it could before. Full rationale is in
   `apps/api/app/rate_limit.py`'s module docstring and `_admission_key`.

3. **New settings read via `os.environ`, not `app_shared.config.Settings`**
   — per the orchestrator's explicit instruction (PB-2 held `config.py`
   for this run). Affected: `REDIS_SOCKET_TIMEOUT_SECONDS` /
   `REDIS_CONNECT_TIMEOUT_SECONDS` (`redis_client.py`),
   `DB_STATEMENT_TIMEOUT_MS` / `DB_POOL_ACQUIRE_TIMEOUT_SECONDS`

   five need a follow-up to become typed `Settings` fields in

## Notes for reviewer
- `_client_ip()` (rate_limit.py) reads `request.client.host` only — it
  does not honor `X-Forwarded-For`/`X-Real-Ip`. This is an
  admission-control bucket key, not a security identity, so a spoofed
  header here only lets an attacker choose which IP bucket their own
  unauthenticated traffic lands in; it cannot bypass the limiter or
  attribute traffic to a different caller. If this API sits behind a
  reverse proxy in production, `_client_ip` is the place to add trusted
  proxy-header support later.
- `override_statement_timeout` in database.py is new, unused-in-repo
  plumbing (no caller wired yet) — it satisfies "keep an override hook
  for maintenance tasks" from the packet's task-specific notes, but no
  existing sweep/maintenance code path calls it. A follow-up should wire
  it into whichever long-running sweep needs to exceed the
  process-wide `DB_STATEMENT_TIMEOUT_MS`.

  "Postgres with statement_timeout forced" half of the acceptance text

  DB call; no real Postgres is involved, matching the constraint.
