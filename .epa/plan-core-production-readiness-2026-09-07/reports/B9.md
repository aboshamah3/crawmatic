Per the packet's own precedent for exactly this situation ("If B9 needs a new setting, read it via `os.environ`... note it for a later config.py consolidation"), I implemented and fully unit-tested the rule LOGIC now (each is exercised against a real `OpsSnapshot` with the attribute attached via `object.__setattr__`, since the dataclass is `frozen=True` but not `slots=True`) and left the snapshot/emit wiring as a named follow-up. This is a net addition (none of these 8 checks exist at all today) with zero change to current production alerting behavior — nothing that fires today stops firing, and nothing new fires until that follow-up lands. The 1 rule that IS live today (`breaker.evaluation_lag`) reads the already-wired `snapshot.breaker.seconds_since_evaluation` field, so it fires in production immediately.
