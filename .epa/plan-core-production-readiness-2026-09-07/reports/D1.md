## Deviations

1. **Steps 2, 3 and 4 are DEFERRED (as the packet instructs).** No Railway environment, service,
   variable or volume was created, modified or deleted; nothing was deployed; nothing was spent.
   `docs/ops/STAGING_ENVIRONMENT.md` and `docs/ops/FLEET_TEST_2026-09.md` carry the exact commands,
   the pass bar (≥ 99% terminal within 24 h, no unbounded queue, rollup < 30 min, pool wait p95
   < 100 ms) and empty measurement rows. Impact: none — this is the assumption's answer 2 shape.
2. **A third test file, `tests/unit/test_fleet_test_report_gates.py` (33 tests).** The packet's
   Test: line names two files. `scripts/fleet_test_report.py` is the *acceptance instrument* for
   the whole fleet test — whether the 100-store commitment is evidenced is whatever its table says
   — and shipping it untested would have been the worse choice. Every one of the 12 rows gets both
   a pass/fail case and a no-input case, because the failure that matters is "a missing measurement
   read as PASS".
3. **`tests/benchmarks/test_rollup_500k.py` (C7's file, outside D1's declared Scope) was modified.**
   The packet assigns the *run* of this benchmark to D1, and it could not run at all:
   (a) `variant_ids` collected `variant.id` immediately after `session.add()`, before the INSERT
   that evaluates `Base.id`'s `default=new_uuid7`, so the list was N `None`s and seeding died with
   `invalid input syntax for type uuid: "None"`; (b) the observation seed named
   `created_at`/`updated_at`, which `price_observations` does not have (it is the one
   workspace-scoped model that deliberately omits `TimestampMixin`). Both fixed minimally, each
   with a comment naming D1 as the origin. A third change — `ANALYZE price_observations` /
   `variant_price_states` after the bulk seed — is explained in Notes below.
4. **The seeder writes a `domain_rules` row**, which the packet's file list does not mention.
   Without it the whole 100-store fleet contends for `FLEET_HOST_CONCURRENCY_DEFAULT` = 6
   simultaneous requests against the single fixture host and the run measures that number instead
   of the platform. Defaults (240 concurrent / 4,000 per minute) are sized ~2× above audit §10's
   30.85 physical attempts/second and are both CLI flags.
5. **`--allow-loopback-origin`.** The seeder validates every URL it writes with the production
   save-time SSRF validator (`validate_competitor_url`), which correctly rejects `localhost`,
   `*.railway.internal` and every private IP — so the local smoke could not have run at all. The
   flag widens acceptance to **loopback addresses only** (checked against the parsed IP, so
   `10.0.0.0/8`, `192.168.0.0/16` and `169.254.169.254` stay refused even with it on) and is
   unit-tested to that exact boundary. Conservative reading of a low-impact reversible choice.
6. **`interval_minutes=1440` + a jittered `next_run_at`, not `cron_expression`.** Audit §10's
   stagger is 14.4 minutes, which a 5-field UTC cron cannot express; rounding to 14 or 15 would
   either bunch the fleet or drift it out of a 24-hour cycle. `refresh_rules`' `exactly_one_cadence`
   CHECK makes this a real either/or, so it is stated in the code and in the test.
7. **The fixture origin's competitor rows are seeded `legal_status=APPROVED`,
   `robots_policy=IGNORE_AFTER_APPROVAL`.** Leaving them at their `REVIEW_REQUIRED` defaults would
   make the whole fleet ineligible and the test would measure nothing. Defensible only because the
   "competitor" is our own fixture service; asserted, with that reasoning, in a test.
8. **`pyproject.toml` edited** (one entry appended to `[tool.uv.workspace] exclude`). Mechanically
   required: `apps/*` would otherwise claim `apps/fixture-origin` as a workspace member and, having
   no `pyproject.toml`, break every `uv run` in the repo — the `apps/dr-backup` comment says so
   explicitly. `uv lock --check` confirms `uv.lock` is unchanged.

## Notes for reviewer

1. **The biggest finding of this task: the rollup batch statement is catastrophically
   plan-sensitive to stale statistics.** The first benchmark attempt had **not completed one batch
   of 500 variants over 100,000 freshly bulk-loaded observations after 18 minutes** at 100% CPU. I
   localised it while it ran, and it is not the SQL: the `driver` CTE alone is **131 ms**, `driver`
   + `latest_per_match` + the aggregate is **175 ms**, the whole statement in `dry_run` form
   (identical CTEs, no INSERT) is **0.14 s**, and after `ANALYZE` the real write batch of 500 is
   **0.19 s**. The planner had chosen a nested loop from statistics that still described the
   partition as empty because autoanalyze had not caught up with the bulk load. **A freshly
   restored or freshly seeded staging database is exactly that case**, so
   `docs/ops/STAGING_ENVIRONMENT.md` §5 now requires `VACUUM ANALYZE` before the first rollup and
   `docs/ops/FLEET_TEST_2026-09.md` §2.2 records the numbers. Nobody watching a staging rollup
   "hang" should record it as a capacity failure. This is worth a look from whoever owns C7/C8 —
   production stats are warm so it is not a live incident, but a partition that has just been
   created (monthly rollover) is a smaller version of the same situation.
2. **Everything in `apps/fixture-origin/` is untested against a real Railway deploy.** The
   Dockerfile and `railway.json` are written, never built, never deployed (no spend). The app
   itself was run under `uvicorn` locally and served 118 real requests correctly.
3. **`scripts/fleet_test_report.py`'s Recovery row deliberately returns NO DATA when the agreed
   RPO/RTO targets are absent**, even with a measured restore. The audit asks for an *agreed*
   target; inventing one would turn an owner decision into a default. The measured numbers are
   still printed in the detail column.
4. **The Economics row is expected to read NO DATA for the fleet test itself** — proxy credentials
   are absent by design, so `cost_model_drift_ratio` stays `NULL`. D3's real-domain canary is what
   settles that row. Stated in `FLEET_TEST_2026-09.md` §7.
5. **`docs/ops/FLEET_TEST_2026-09.md` §3's 2× offered-load step is written as "add a second daily
   rule", and the seeder deliberately refuses to help** (it is idempotent by workspace slug and
   will not double-seed a catalogue). The SQL sketch is in the doc; whoever runs step 3 should
   sanity-check it against `refresh_rules`' CHECK constraints before running it.
6. **The fixture origin is one host, and all 592,500 checks/day hit it.** Per-domain fairness and
   hot-domain routing (F11/B4) are therefore exercised in their worst configuration, and the
   storage/ledger numbers are under-exercised because the strategy resolver will almost certainly
   pick the HTTP path for a domain with no playbook. Both caveats are in `FLEET_TEST_2026-09.md`
   §7 so no one reads a fleet-test number as a production number.
7. **Production Postgres major, re-confirmed from C11's record rather than re-derived:** the newest
   backup manifests say **18.4/18.6**; `docker-compose.yml`'s `postgres:17.5-bookworm` is the stale
   pin. `STAGING_ENVIRONMENT.md` §2 says the staging instance must be created at the major the
   manifest names, or `pg_restore` refuses the newer-dump-into-older-server direction. My local
   smoke used 17.5 (an empty `alembic upgrade head`, not a restore), which is why its numbers are
   labelled as local and not as staging measurements.
