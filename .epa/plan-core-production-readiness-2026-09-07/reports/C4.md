## Notes for reviewer

**C1 carry-forward (a) — CLOSED, and here is exactly how far.**
Both named call sites now pass `budget=`:
- `tasks_jobs._resolve_domains_and_modes` (the old line 611) builds an `AttemptBudget` from `SCRAPE_TARGET_MAX_PHYSICAL_ATTEMPTS`, the target's own `started_at`/`created_at` + `SCRAPE_TARGET_DEADLINE_SECONDS`, and the domain's `recovery_probe_fraction`. `redis`/`scrape_job_id`/`settings` are **optional keyword parameters**, so the two production callers (`dispatch_job` and the stall re-plan) wire them and every existing test keeps the pre-C1 path. A terminal refusal calls `mark_target(... FAILED, error_code=decision.refusal, only_if_status=(PENDING, DEFERRED))` and drops the target from the plan.
- `targets.load_targets` (the old line 871) does the same, collecting refusals into `refusals_by_match`, finalizing them in one pass before any `SpiderTarget` is built, and skipping those matches.
The deadline is anchored on the **target's** clock, not the job's, so a re-plan or a stall recovery re-derives the same instant instead of granting a fresh window — worth a second look, it is the property that makes the bound real.

**C1 carry-forward (b) — wired for the HTTP leg only.** `resolve_request_timeout_seconds(target)` (precedence: learned `domain_rules.request_timeout_seconds` → `access_policy.timeout_ms` → `None`, i.e. Scrapy's `DOWNLOAD_TIMEOUT`, which is already `SCRAPE_DOWNLOAD_TIMEOUT_SECONDS`) is consumed by `apps/scrapers/price_monitor` only. **The browser spider is NOT wired**: its bound is `browser_timeout_ms`/`SCRAPE_BROWSER_*`, a different knob on a different clock, and mapping a request timeout onto a Playwright navigation timeout is a judgement I did not have evidence for. Follow-up for whoever owns browser timeouts. Returning `None` rather than the global was deliberate — it keeps `download_timeout` absent for a target with neither source (pinned by the pre-existing `test_request_without_policy_has_no_download_timeout`) and keeps the function pure enough for the reactor thread.

**The fallback cap fails OPEN.** `fallback_attempts_used()` returns 0 on a Redis error and `charge_fallback_attempt()` swallows one, so a cache outage makes the cap inert rather than refusing the expensive rung fleet-wide. Same reasoning as C1's (a fabricated refusal becomes persisted evidence and poisons the optimizer), and the physical-attempt budget plus the wall-clock deadline still bound the spend. Pinned by `test_a_gate_without_the_counter_makes_the_cap_inert_not_wrong`.

**The cap bites on the reactor-side ladder, which is where browser escalation actually happens.** `SpiderTarget.playbook_strategy` carries the frozen `PlaybookStrategy` loaded off-reactor by `load_targets`, and `next_strategy_attempt` passes it in. Reading it on the reactor is pure; **but a budget passed there still does Redis I/O**, exactly as C1 warned. Today the two spiders call `next_strategy_method(target, outcome)` with no budget, so the *cap* is enforced only where a budget is present. Moving those `parse`-thread calls off-reactor is the remaining piece and is a spider change, out of this packet's scope.

A DB trigger or a seed-lint is the natural follow-up.

That is a real follow-up, not a defect: the correctness half (no wrong shared fetch) is in place, the savings half needs the dispatch layer to know the exit country before planning.
