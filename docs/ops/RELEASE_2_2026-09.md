### Finding 1 (CRITICAL, was release-blocking; **FIXED AT SOURCE 2026-09-08**) — migration `b6e5d1c94a72`'s in-migration backfill silently updates ZERO rows against a real, RLS-protected production table

`alembic upgrade head` failed with:
```
psycopg.errors.NotNullViolation: column "scrapyd_job_id" of relation "dispatch_intents" contains null values
[SQL: ALTER TABLE dispatch_intents ALTER COLUMN scrapyd_job_id SET NOT NULL]
```

**Root cause**, confirmed by direct inspection of the restored copy: `dispatch_intents` carries
`FORCE ROW LEVEL SECURITY` with the standard fail-closed policy
(`libs/shared/app_shared/models/rls.py`: `{col} = NULLIF(current_setting('app.workspace_id',
true), '')::uuid` — "an absent or empty workspace context matches **zero rows**, never all rows").
The migration's own backfill —

```sql
UPDATE dispatch_intents SET scrapyd_job_id = intent_id::text
 WHERE scrapyd_job_id IS NULL OR scrapyd_job_id !~ '<uuid-shaped-regex>';
```

— runs as `crawmatic_migrate` (confirmed `rolbypassrls=False` on the restored copy) with no
`app.workspace_id` GUC set. Per the fail-closed policy this matches **zero rows**, not "every
row" — the backfill is a silent no-op on a live-data restore, and the very next statement
(`ALTER COLUMN scrapyd_job_id SET NOT NULL`) then fails against every pre-existing NULL row. This
is the exact class of bug B1's own migration docstring (`a4e91c7d2b58`) warned about for
`price_observations` and deliberately avoided there with a staged, RLS-aware approach — B2's
`b6e5d1c94a72` (written before B1's finding was cross-referenced) hit it for real. **Measured on
this backup set: 2,040 affected rows, all in ONE workspace** — i.e. this is not a hypothetical,
it is production data that would break the real migration exactly as it broke both rehearsals.

**Original workaround (verified end-to-end on a second independent rehearsal against the SAME
dump, and now SUPERSEDED):** run the identical backfill as `crawmatic_auth` (the BYPASSRLS system
role) immediately before the migration. Verified at the time: 2,040 → 0 affected rows, then
`alembic upgrade head` reaches `e7b34c0af219` cleanly. **Do not run this — it is no longer a
release step.**

#### ✅ FIXED AT SOURCE — EPA B2-fix1, 2026-09-08

`b6e5d1c94a72` no longer issues any DML against `dispatch_intents`. The backfill is now the
`USING` expression of the type change itself:

```sql
ALTER TABLE dispatch_intents ALTER COLUMN scrapyd_job_id TYPE UUID
  USING CASE WHEN scrapyd_job_id ~ '<uuid-shaped-regex>'
             THEN scrapyd_job_id::uuid ELSE intent_id END;
ALTER TABLE dispatch_intents ALTER COLUMN scrapyd_job_id SET NOT NULL;
```

Row-level security qualifies DML (`SELECT`/`INSERT`/`UPDATE`/`DELETE`); it does **not** qualify a
table rewrite. So the value transformation reaches every row as `crawmatic_migrate`, with no
`BYPASSRLS` role, no `SET ROLE`, no operator pre-step, and no temporary
`NO FORCE ROW LEVEL SECURITY` window that would disarm the table's isolation mid-migration. This
is the same technique `a4e91c7d2b58` used for `price_observations.attempt_uuid` (a volatile
`server_default` applied *during* its rewrite) and for the same reason. `SET NOT NULL` then
re-scans the relation as DDL, so it remains a real assertion: if the rewrite ever stops covering
every row, the migration fails loudly rather than shipping a half-backfilled column. Note that a
`SELECT`-based self-check inside the migration would have been useless — under the same policy it
also sees zero rows and "passes" precisely when the backfill did nothing.

Regression test: `tests/unit/test_migration_offline_dispatch_intent_backfill.py` renders the
revision offline and fails if it ever emits `UPDATE`/`INSERT`/`DELETE` against `dispatch_intents`
again, or if the `USING` expression loses either backfill branch. Confirmed RED against the old
migration text before the fix landed.

**Release-day action: none.** Keep the read-only pre-check below as *verification* only.

```sql
-- VERIFICATION ONLY (read-only, safe on production, any role that can read the table).
-- Before the migration this reports the rows the rewrite will normalise; after it, the column is
-- already uuid NOT NULL and the query no longer applies.
SELECT count(*) AS bad_rows, count(DISTINCT workspace_id) AS distinct_workspaces
FROM dispatch_intents
WHERE scrapyd_job_id IS NULL
   OR scrapyd_job_id !~ '^[0-9a-fA-F]{8}-?[0-9a-fA-F]{4}-?[0-9a-fA-F]{4}-?[0-9a-fA-F]{4}-?[0-9a-fA-F]{12}$';
```
```sql
-- VERIFICATION ONLY, AFTER "alembic upgrade head": the column must be uuid NOT NULL with no NULLs
-- left behind. Run as crawmatic_auth (BYPASSRLS) so the count is not itself filtered by RLS.
SELECT data_type, is_nullable FROM information_schema.columns
 WHERE table_name = 'dispatch_intents' AND column_name = 'scrapyd_job_id';
-- expect: uuid | NO
SELECT count(*) FROM dispatch_intents WHERE scrapyd_job_id IS NULL;  -- expect 0
```

```sql
-- NOTE: the model's actual column is product_variant_id (Release 1 §2.10's analogous query names
```
