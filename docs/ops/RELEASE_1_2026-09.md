### Finding 1 — the Postgres major is 18, not 17.5. Fix the compose pin.

The dump was **not assumed** to be a given major. `scripts/dr/rehearse_upgrade.sh` reads
`.targets.engine.server_version` from the backup manifest and cross-checks it against the dump's own
`pg_restore -l` TOC header before starting anything:

```
manifest server_version = "18.4 (Debian 18.4-1.pgdg13+1)"
pg_restore -l header     = "Dumped from database version: 18.4 (Debian 18.4-1.pgdg13+1)"
```

Both agree: **production is PostgreSQL 18.4.** `docker-compose.yml`'s `postgres` service is pinned to
`postgres:17.5-bookworm` — **this pin is stale; the plan's tech-stack line ("PostgreSQL 18") is the
one that is right.** Restoring an 18.x dump into a 17.5 server is the wrong-direction major-version
mismatch `pg_restore` refuses, so the rehearsal script never uses the compose `postgres` service —
it starts its own throwaway container image-pinned to whatever major the manifest says, every run.

**Owner follow-up (tiny, not done here — `docker-compose.yml` is out of A10's file scope):**
```bash
# in docker-compose.yml, service `postgres`:
-  image: postgres:17.5-bookworm
+  image: postgres:18-bookworm
```
This does not block Step 2 below (the release deploys straight to Railway Postgres 18, never through
the local compose stack), but every future local integration-test run against compose Postgres is
running the wrong major until this is bumped.

### Finding 2 — `provision_db_roles.sql` §8 does not adopt FUNCTION ownership; the rehearsal needed
an extra step to get a clean `alembic upgrade head`

The **first** rehearsal run failed at `alembic upgrade head` with:
```
psycopg.errors.InsufficientPrivilege: must be owner of function network_operation_allocations_check_total
```
Root cause: a fresh restore leaves every function owned by whichever role ran `pg_restore` (the
connecting superuser). `provision_db_roles.sql` section 8 ("adopt ownership") only reassigns
**table and sequence** ownership (`relkind IN ('r','p','S')`) into `crawmatic_migrate` — it has no
equivalent step for functions/triggers, so `CREATE OR REPLACE FUNCTION` in migration `b7c1d2e3f4a5`
failed as `crawmatic_migrate` even though `crawmatic_migrate` now owned every table.

`scripts/dr/rehearse_upgrade.sh` closes this gap **inside its own throwaway database only** (it does
not, and structurally cannot from A10's file scope, modify `provision_db_roles.sql`) with an explicit,
separately-logged step that reassigns function ownership the same way section 8 does for tables:
```sql
DO $$
DECLARE rel record; moved int := 0;
BEGIN
    FOR rel IN
        SELECT p.oid::regprocedure AS ident
        FROM pg_proc p
        JOIN pg_roles r ON r.oid = p.proowner
        JOIN pg_namespace n ON n.oid = p.pronamespace
        WHERE n.nspname = 'public' AND r.rolname <> 'crawmatic_migrate'
    LOOP
        EXECUTE format('ALTER FUNCTION %s OWNER TO crawmatic_migrate', rel.ident);
        moved := moved + 1;
    END LOOP;
    RAISE NOTICE 'function ownership adopted for % function(s)', moved;
END $$;
```
**Whether this also bites the real production migrate step is not known from here** — it depends on
whether `crawmatic_migrate` already owns every function a pending migration modifies in production
today (built up from whatever role ran previous migrations). §6.5 below makes checking this, and
fixing it if needed, a mandatory pre-flight — read-only until a fix is actually required, and the fix
is the identical one-liner `ALTER FUNCTION ... OWNER TO crawmatic_migrate;` per offending function,
never a schema change.

**Follow-up recommendation (not done here, `provision_db_roles.sql` is out of A10's file scope):**
extend section 8's ownership-adoption loop to also cover `pg_proc` the same way it covers
`pg_class` — then §6.5 below becomes unnecessary. Flagged for whoever next touches
`provision_db_roles.sql` (A3's owner).

### Finding 3 — Step 2/§6's literal order (provision once, then migrate) leaves migration-created
tables grant-less; provisioning must run **twice**

The first rehearsal run (after fixing Finding 2) reached `alembic upgrade head` cleanly, then
`verify_grants.py` FAILed with 4 `MISSING` findings, all on `control_plane_rules` — a table created
by migration `b7c1d2e3f4a5`→`c8d2e3f4a5b6`, which did not exist yet when `provision_db_roles.sql` ran
before the migration. This is **documented, intentional behavior** in `provision_db_roles.sql`
section 5's own comment: *"A table named in the manifest that does not exist yet in this database
... is skipped with a WARNING rather than aborting the whole idempotent run."* — necessary because
`crawmatic_migrate` must exist *before* `alembic` can even authenticate as it, so provisioning cannot
simply move to after the migration.

The fix costs nothing because `provision_db_roles.sql` is fully idempotent by design: **run it
again after the migration.** §6 and §6.5 below encode this as the real sequence — this is not
optional and not a deviation from the plan's step 6/7, it is the concrete mechanics of "provision
roles/grants" being one *logical* step that spans two invocations. The rehearsal script performs
both passes and finishes with `verify_grants.py` reporting 0 FAIL (3 benign `WARN`s remain — monthly
partition children and `workspace_usage_v` genuinely absent from the static manifest by design; see
`verify_grants.py`'s own docstring and `reports/A3.md`).

### 2.10 — Smoke: one 20-target S-Tech direct job via the API

S-Tech (`stech.ink`) is the platform's **direct** (non-proxied) canary domain (see
`alembic/versions/d9a46612bcc8_domain_playbooks_state.py`, `_ACTIVE_SEED_DOMAINS`). There is no
batch "run N targets" endpoint — a job fans out from one variant's competitor matches
(`app_shared.jobs.service.create_variant_job`) — so pick a variant with ≥20 live `stech.ink`
competitor matches:

```bash
# Find a candidate variant (read-only), 20+ stech.ink matches:
psql "<production DSN, read-only>" -Atqc "
SELECT cpm.variant_id, count(*) AS stech_targets
FROM competitor_product_matches cpm
JOIN competitors c ON c.id = cpm.competitor_id
WHERE c.domain = 'stech.ink'
GROUP BY cpm.variant_id
HAVING count(*) >= 20
ORDER BY count(*) DESC
LIMIT 1;
"
```
```bash
# Dispatch the job (requires a jobs:write-scoped API key):
curl -s -X POST https://<engine-host>/v1/jobs/run/variant/<variant_id> \
  -H "Authorization: Bearer <api key>" | tee /tmp/smoke-job.json
JOB_ID=$(jq -r .id /tmp/smoke-job.json)
```
```bash
# Poll until targets pass through STARTED and persisted_at is set (A5):

  jq '{status, targets: [.targets[] | {status, started_at, persisted_at}]}'
```
